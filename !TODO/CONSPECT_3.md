## 2. MemorySystem — аллокаторы по принципу ZII

### 2.1. Что такое ZII

**Zero Is Initialization**: объект, все байты которого нули, — корректный объект в «пустом» состоянии.

| Тип | Что значит ноль |
|---|---|
| `ECS::Entity{}` | «нет сущности» |
| `WindowSystem::InputState{}` | ничего не нажато |
| `MemorySystem::Arena{}` | пустая арена: ничего не выделяет, но и не падает |
| `MemorySystem::ArenaMarker{}` | начало арены |
| `std::span<T>{}` | пустой список |

Отсюда правило модуля: **аллокаторы всегда отдают нулевую память**. Конструктор не нужен,
забыть инициализировать поле невозможно. Типы, которые в ней живут, проверяются концептом
`ZeroInitializable` (trivially copyable + trivially destructible). Смысл нуля — часть контракта типа.

### 2.2. Состав

| Класс | Назначение | Пример |
|---|---|---|
| `VirtualRegion` | резерв адресов ОС, подтверждение страниц по мере роста (Windows: VirtualAlloc, POSIX: mmap/mprotect) | свой аллокатор |
| `Arena` | линейная арена: выделение — сдвиг указателя, освобождение — откат | уровень, кадр, запрос |
| `ArenaScope` | запоминает позицию и откатывает в деструкторе | временная память функции |
| `DoubleArena` | две арены, меняются каждый тик | данные, живущие один тик после создания |
| `Pool<T>` | свободный список внутри освобождённых блоков | частицы, снаряды |
| `ArenaResource` | `std::pmr::memory_resource` поверх арены | `std::pmr::vector` во временной памяти |

### 2.3. Главное решение: где платить за нули

```
[ занято .............. | нули ........................ | не подтверждено ....... ]
0                  position                        committed                 capacity
```

**Инвариант:** всё выше `position` — нули.
- **push** ничего не зануляет. Память уже нулевая, это просто выравнивание и сдвиг указателя (~4 нс).
- **pop_to / reset** зануляют `[marker, position)`. Платим один раз и только за то, что реально использовали.
- **Новые страницы** ОС отдаёт нулевыми, поэтому рост виртуальной арены тоже бесплатен по нулям.

Альтернатива — «занулять при выделении» — стоила бы `memset` на каждый push.
При схеме «много мелких выделений, потом reset кадра» это медленнее.

**Адреса стабильны.** Резерв делается сразу (по умолчанию шаг подтверждения 64 КиБ).
Указатель в арену никогда не «переезжает», в отличие от `std::vector`.

**Начало жизни объекта.** Байты уже нули, но формально объект `T` в них ещё не существует.
`start_lifetime_as_array<T>()` — замена C++23 `std::start_lifetime_as_array` через `memmove`
(он неявно создаёт объекты). Компилятор убирает этот вызов целиком.

### 2.4. DoubleArena — та же модель, что у шины

Шина показывает событие тика N ровно в тике N+1. DoubleArena делает то же для памяти:
выделенное в `current()` в тике N читается через `previous()` в тике N+1 и освобождается
следующим `swap()`. Это задел под события, которые несут ссылку на большие данные
(путь, список видимых объектов): событие плоское, а данные лежат в арене тика.

### 2.5. Замеры (GCC 14, RelWithDebInfo)

| Замер | MemorySystem | Для сравнения |
|---|---|---|
| выделение 32 Б | Arena::push ~4.3 нс | malloc ~14 нс |
| 10 000 объектов + освобождение всех | ~36–38 мкс | new/delete ~155–170 мкс |
| освободить + выделить один объект | Pool ~4.6 нс | delete + new ~13 нс |
| `pmr::vector`, 100 000 push_back | 60–80 мкс | `std::vector` 60–80 мкс (в пределах шума) |
| цена ZII: reset после 1 МиБ | ~18–20 мкс (≈ 50 ГиБ/с) | — |

Зануление при reset идёт со скоростью `memset`. Для арены кадра на несколько мегабайт
это десятки микросекунд — меньше 1% кадра на 60 Гц.

### 2.6. Ограничения

- Арена и пул **не потокобезопасны**: одна арена — один поток. Для многопоточной шины
  (локальные буферы писателей из обсуждения) нужны арены на поток.
- ArenaResource не освобождает память по одному: контейнеры, которые долго растут,
  оставляют в арене старые буферы. Помогает заранее вызванный `reserve()`.

## 3. ECSSystem — сущности с поколением

### 3.1. Что было не так в старой версии

| Было | Проблема | Стало |
|---|---|---|
| `Entity = uint32_t` | нет поколения: ссылка на погибшую сущность попадала в новую в том же слоте | `Entity {index, generation}`, `valid()` |
| `MAX_ENTITIES = 10000`, `std::array<T, 10000>` в каждом пуле | жёсткий предел; ~200 КБ на тип компонента даже без сущностей | страницы по 4096 слотов по требованию |
| `bitset<64>` маски, `MAX_COMPONENTS = 64` | предел типов компонентов | предела нет |
| `for_each` шёл по первому типу | `view<Position, Burning>` проходил все Position | обход по наименьшему пулу |
| `PoolAllocator` внутри ECS, поиск указателя перебором блоков | O(блоков) на free | удалён, замена — `MemorySystem::Pool` |
| модуль не входил в сборку | — | включён, 27 тестов |

### 3.2. Сущность и поколение

```
create()             → {5, gen 1}
destroy({5, 1})        слот 5 свободен
create()             → {5, gen 2}      тот же слот, новое поколение
world.valid({5, 1})  → false
world.get<T>({5, 1}) → nullptr         старая ссылка не видит компонент новой сущности
```

Это ровно то, что Ecosystem делает вручную (`Handle` + Life). Пример `02_generations.cpp`
воспроизводит сценарий «лиса целится в зайца, заяц умер, в слоте родился новый».

**ZII:** `Entity{}` = «нет сущности». Слот 0 не выдаётся, у живых поколение ≥ 1.
Компонент `Target { ECS::Entity entity; }` по умолчанию означает «цели нет» без отдельного флага.

### 3.3. Хранение: страничный sparse set

```
sparse (по слоту, страницы по 4096):   [ 0 | 3 | 0 | 1 | 2 | 0 … ]    0 = нет компонента
dense entities:                         [ e3 | e4 | e1 ]
dense components:                       [ c3 | c4 | c1 ]
```

В sparse хранится «индекс в dense + 1», поэтому **ноль означает «компонента нет»**.
Новая страница выделяется обнулённой (`make_unique<uint32_t[]>`) и готова без инициализации —
тот же ZII, что в MemorySystem.

### 3.4. Выборки

- Обход идёт по **наименьшему** пулу. Ведущий пул выбирается один раз, и цикл специализирован
  под него на этапе компиляции: из ведущего пула компонент берётся по индексу, из остальных — поиском.
- Обход идёт **с конца**, поэтому внутри `each` можно уничтожить **текущую** сущность.
  Создавать сущности, добавлять компоненты и удалять другие сущности нельзя — собрать и применить после
  (пример `03_systems.cpp`).
- `view<Position, const Velocity>` — `const` даёт доступ только на чтение.

### 3.5. Замеры

| Замер | ECS | «Голые» `std::vector` |
|---|---|---|
| обход 1 компонента, 100 000 | ~1.4 млрд/с | ~3–4 млрд/с (компилятор векторизует) |
| обход 2 компонентов у всех, 100 000 | ~0.34–0.47 млрд/с | ~2.2–3 млрд/с |
| обход 2 компонентов, пересечение 1% из 100 000 | 1 000 сущностей за ~3–4 мкс | — |
| `get` по случайной сущности | ~6 нс | — |
| destroy + create + 2 компонента | ~73–97 нс | — |

**Честно о разрыве.** Первая версия выборки давала 0.17 млрд/с на двух компонентах.
После специализации под ведущий пул стало вдвое быстрее, но до «голых» массивов остаётся 5–6×.
Это цена sparse set: второй компонент ищется в своём пуле (страница → индекс → сверка сущности).
Для Sandbox-масштабов (тысячи сущностей) это микросекунды. Если станет узким местом,
следующий шаг — «группы» (пулы держат общие сущности в одинаковом порядке, как в EnTT).

## 4. WindowSystem — окно, ввод, события

### 4.1. Что закрыто из списка конспекта 1

| Проблема (конспект 1, раздел 9) | Решение |
|---|---|
| нет мыши и колеса | `InputState`: кнопки, курсор, смещение, колесо, текст |
| нет `set_title`, framebuffer'а, vsync, времени | `set_title`, `framebuffer_size`, `content_scale`, `set_vsync`, `time` |
| один слушатель клавиш, его занимал App | `WindowEvents`: сколько угодно подписчиков на 7 событий |
| Esc жёстко закрывал окно | решает игра; `WindowConfig::close_on_escape` для примеров |
| счётчик окон уменьшался, даже если glad не загрузился | `create()` → `std::expected`: либо готовое окно, либо ошибка, всё уже освобождено |
| перемещение окна ломало указатель GLFW | состояние в куче (`Impl`), адрес стабилен |
| окно вызывало `glViewport` на resize | окно не рисует: событие `framebuffer_resized` |

### 4.2. Модель ввода

| Вопрос | Метод | Когда `true` |
|---|---|---|
| зажата? | `down` | с нажатия до отпускания |
| нажали в этом кадре? | `pressed` | один кадр; нажатие+отпускание внутри кадра тоже ловится |
| отпустили? | `released` | один кадр |

`InputState` не зависит от GLFW. Окно только передаёт в него события и вызывает `begin_frame()`.
Поэтому ввод тестируется без дисплея, а записанный ввод можно воспроизвести (`02_input_replay.cpp`).
При потере фокуса всё «отпускается» — клавиши не залипают.

Методы `inject_*` отправляют событие тем же путём, что и ОС: в InputState и всем подписчикам.

### 4.3. Что изменилось в Core

| Было в Core::App | Стало |
|---|---|
| `static App* s_active` ради колеса мыши | `input().scroll()` |
| `glfwGetKey / glfwGetMouseButton / glfwGetCursorPos` | `input().down / mouse_pressed`, `cursor_in_framebuffer()` |
| `glfwSetWindowTitle`, `glfwGetFramebufferSize`, `glfwGetTime` | `set_title`, `framebuffer_size`, `Window::time` |
| `onKeyPress` (единственный) | подписка `events().key` |
| заголовок WindowSystem подключался как SYSTEM из-за предупреждений | заголовок чистый, обход удалён |

FallingSand и Colony с `--ticks 375` дают **ту же** статистику шины, что до переноса:
поведение не изменилось.

### 4.4. Замеры

| Замер | Время |
|---|---|
| begin_frame + 8 событий клавиш | ~20 нс |
| `down(key)` | ~1 нс |
| событие 8 подписчикам | ~20 нс |

## 5. Как ZII связывает три модуля

```
MemorySystem:  память выдаётся нулевой            → объект готов без конструктора
ECSSystem:     Entity{} = «нет сущности»           → компонент-ссылка без флага «есть цель»
               страница sparse из нулей = «пусто»  → новая страница без инициализации
WindowSystem:  InputState{} = «ничего не нажато»   → нет состояния «ещё не инициализирован»
               Window{} / ListenerId{} — безопасные «пустые» объекты
```

Общий принцип: у каждого типа **нулевое состояние осмысленно и безопасно**. Это убирает
целый класс ошибок «забыли инициализировать» и делает массовое выделение дешёвым.

## 8. Команды

```sh
# сборка и тесты
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build
ctest --test-dir build                        # на Linux без дисплея: xvfb-run ctest --test-dir build

# отдельный модуль
cmake -S Modules/MemorySystem -B build/mem && cmake --build build/mem && ctest --test-dir build/mem

# с санитайзерами
cmake -S Modules/ECSSystem -B build/ecs-asan -DCMAKE_BUILD_TYPE=Debug -DECSSYSTEM_SANITIZE=ON

# бенчмарки
build/bin/MemorySystemBenchmarks
build/bin/ECSSystemBenchmarks --benchmark_filter=View
build/bin/WindowSystemBenchmarks

# документация (нужен doxygen)
cmake --build build --target MemorySystemDocs ECSSystemDocs WindowSystemDocs
# → build/Modules/<Name>/docs/html/index.html

# примеры
build/bin/MemorySystemExample_01_arena_basics
build/bin/ECSSystemExample_02_generations
build/bin/WindowSystemExample_01_window_input     # окно; Esc — выход
```
