# ECSSystem — конспект для изучения и переписывания

Header-only, ~680 строк: `src/include/ECSSystem/{Entity,ComponentPool,View,World}.hpp`. Пространство имён — `ECS` (не `ECSSystem`). Зависимостей нет.

## 1. Зачем и главная идея

ECS хранит **состояние мира**: какие есть сущности и что у них за данные. Пара к `EventSystem`: события говорят, *что случилось*, компоненты — *как есть сейчас*.

Три решения, на которых всё стоит:
1. **Сущность — ссылка с поколением** (`{index, generation}`, 8 байт), а не объект и не голый номер.
2. **Компоненты — в sparse set**: плотный массив для обхода + разреженный индекс для быстрого поиска.
3. **ZII:** `Entity{}` = «нет сущности»; страницы индекса обнулены = «компонента нет».

## 3. Как устроено

### 3.1 Сущность и реестр
- `Entity{index, generation}`; слот 0 **никогда не выдаётся**, поколение живых ≥ 1 → нулевая ссылка не равна ни одной живой. `is_null()` смотрит только `index`.
- `EntityRegistry`: `m_generations[slot]`, `m_alive[slot]`, стек свободных слотов (LIFO — последний освобождённый выдаётся первым, он «горячий в кэше»).
- `create()`: берёт слот из `m_free` или добавляет новый, **увеличивает поколение**, помечает живым.
- `destroy(e)`: если `valid(e)` — слот в `m_free`, `alive=false`. Поколение растёт при следующем `create`, а не при `destroy`; валидность всё равно корректна, потому что `valid` проверяет и `alive`, и поколение.
- `valid(e)` = ненулевой индекс, в диапазоне, живой, поколение совпадает → устаревшая ссылка «видит», что сущность умерла и слот уже занят новой.
- `clear()`: все слоты в свободные (в обратном порядке, чтобы выдача шла по возрастанию), **поколения сохраняются** — старые ссылки остаются невалидными.

### 3.2 `ComponentPool<T>` — sparse set
```
sparse (страницы по 4096 слотов): [ 0 | 3 | 0 | 1 | 2 | 0 … ]   0 = нет, иначе (индекс в dense + 1)
dense entities:                   [ e3 | e4 | e1 ]
dense components:                 [ c3 | c4 | c1 ]               ← системы идут здесь
```
- `emplace(e, args...)`: если слот индекса уже занят **той же** сущностью — компонент перезаписывается (`T{args...}`); если занят **прошлым поколением** — старый компонент удаляется; иначе push в конец dense и запись в sparse. Компонент создаётся `T{...}` — фигурные скобки: нужен агрегат или подходящий конструктор.
- `find(e)`: страница → значение → сверка `m_entities[dense-1] == e` (сверка с поколением и делает устаревшие ссылки безопасными).
- `remove(e)`: swap-and-pop: последний элемент ставится на место удалённого, его sparse-индекс обновляется; O(1).
- Страницы (`unique_ptr<uint32_t[]>`) создаются по требованию **нулевыми** (`make_unique<T[]>(n)` value-инициализирует) — ноль = «нет» (ZII), инициализировать нечего. Предела числа сущностей нет.
- Ссылка, возвращённая `emplace`/`get`, **действительна до следующего добавления/удаления в этом пуле** (векторы растут).
- `components()` / `entities()` — плотные параллельные спаны для прямых циклов.

### 3.3 `View<Ts...>`
- Набор указателей на пулы (ничего не копирует и не кэширует). Нет пула типа → выборка пуста.
- **Ведущий пул** — наименьший (`smallest_pool`): `view<Position, Burning>` при 100 000 и 1 000 пройдёт 1 000. Остальные компоненты ищутся через `get` (O(1)). Выбор ведущего делается **во время выполнения один раз**, а тело цикла специализируется на него **шаблонно** (`with_driver` + индексная последовательность).
- Обход **с конца** плотного массива: можно безопасно удалить **текущую** сущность (на её место встанет уже пройденная). Добавлять компоненты и удалять **другие** сущности во время обхода нельзя — соберите в список и примените после. Защита `if (row >= driver->size()) continue;` покрывает случай, когда колбэк удалил несколько сущностей.
- Колбэк: `fn(Entity, Ts&...)` или `fn(Ts&...)` — выбор через `is_invocable` (`if constexpr`). `const T` в `Ts` — только чтение.

### 3.4 `World`
- `m_registry` + `vector<unique_ptr<IComponentPool>>`, индекс — `component_id<T>()` (счётчик по порядку **первого обращения** в процессе, `static` на тип). **Не стабилен между запусками** — нельзя сохранять в файл и слать по сети.
- `destroy(e)`: если валидна — `remove` во всех существующих пулах (через интерфейс), затем реестр.
- `emplace<T>` ассертит, что сущность жива. `get`/`has`/`remove` на мёртвой или устаревшей ссылке вернут `nullptr`/`false`.
- `entities_of<T>()` — **копия, отсортированная** по `Entity` (индекс, поколение). Нужна для **детерминизма:** порядок обхода dense-массива зависит от истории вставок/удалений (swap-remove), а сортировка делает его одинаковым при любой истории. Все системы симуляции (`SpellSim`, `Character`) обходят сущности этим списком; копия заодно разрешает менять мир во время обхода. Тот же приём описан в правилах `Math` (п. 2).
- `view<Ts...>()` не создаёт пулы.

## 4. Как использовать

```cpp
ECS::World world;
ECS::Entity rabbit = world.create();
world.emplace<Position>(rabbit, 10.0f, 5.0f);
world.emplace<Velocity>(rabbit, 1.0f, 0.0f);

world.view<Position, const Velocity>().each([](Position& p, const Velocity& v) { p.x += v.x; });

if (auto* t = world.get<Target>(hunter); t && world.valid(t->entity)) { /* цель ещё жива */ }

// детерминированный обход (симуляция):
for (ECS::Entity e : world.entities_of<Character>()) { /* порядок не зависит от истории */ }

world.destroy(rabbit);   // все компоненты убраны; старая ссылка невалидна
```
Идиома «цель»: `struct Target { ECS::Entity entity; };` — по умолчанию «цели нет» без флага; перед использованием `world.valid(target.entity)`.

Где это в проекте: `Character` и `Runes` (исполнение рун на сущностях), `SpellSim` (владеет `World`), игры Colony/Ecosystem/Siege/Swarm/Voxel/CardDuel.

## 5. Что менять осторожно

- **Не используй `view().each` в симуляции, если порядок влияет на результат** — используй `entities_of`. `view` быстрее, но порядок = история (swap-remove). Это самая тонкая ловушка ECS в детерминированном проекте.
- Не добавляй компоненты и не уничтожай чужие сущности внутри `each`: ссылки на компоненты и dense-массивы перестанут быть валидными.
- `component_id` зависит от порядка первого обращения: два процесса (клиент и сервер) дадут разные номера. Для сохранений/сети нужен ID по имени типа.
- `World` не потокобезопасен. Параллельно можно читать разные компоненты, но не изменять структуру (добавление/удаление).
- `std::vector<bool>` для `m_alive` — компактно, но не потокобезопасно даже на чтение соседних бит при записи; учти при многопоточности.
- Цена гибкости: обход 2 компонентов у всех сущностей ~5× медленнее «голых» массивов (замеры в `docs/mainpage.md`). Следующий шаг — «группы» (владеющие выборки), если станет узким местом.

## 6. Упражнения для переписывания

1. Реализуй `component_id<T>()` по имени типа (хеш `typeid(T).name()` или явный `static constexpr name`) и сделай `World` сериализуемым.
2. Добавь `World::sort<T>()` и «группу» `group<A, B>()` — пулы A и B хранят общие сущности в одном порядке; сравни скорость на бенчмарке.
3. Сделай отложенные команды (`CommandBuffer`: `create/destroy/emplace`), применяемые после `each`, и перепиши на них систему, удаляющую чужие сущности.
4. Замени `std::vector<bool>` на `vector<uint8_t>` и посмотри разницу в бенчмарке `create/destroy`.
5. Добавь события «компонент добавлен/удалён» через `EventSystem` — какой слой должен их порождать (`World` или `Pool`) и почему?
