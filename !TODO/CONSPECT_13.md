# Конспект 13 — надёжность и детерминизм: эталоны, именованные хеши, записи в журнале, эксперимент «мир = сид + журнал»

Пункты 1–4 из раздела «Надёжность и детерминизм» конспекта 12.

## 1. Эталонные записи (golden)

`Modules/SpellSim/tests/golden/spellsim_a.rec`, `spellsim_b.rec` — записи двух сценариев (сид 1: прогулка, оба заклинания обоими
способами, «убегающий» цикл; сид 42: движение к краю мира, частые касты у границ чанков) с хешами подсистем на последнем тике. Тест
`Golden*` (`tests/test_golden.cpp`) делает две проверки: (1) повтор закоммиченной записи даёт те же хеши по каждой подсистеме;
(2) сценарий в коде и запись в репозитории совпадают (`Replay::diff`) — правка сценария без пересоздания эталона не пройдёт незамеченной.

**Проверено кросс-компиляторно:** эталоны записаны clang Release, воспроизводятся побитово в **gcc Release, gcc Debug и clang Debug**
(`cmake -S Modules/SpellSim -DCMAKE_CXX_COMPILER=g++ …`). Это самый дешёвый способ поймать недетерминизм по платформам: у кода симуляции
нет float, `-ffast-math`, `std::rand` и порядка обхода по хешам — и тест это подтверждает.

Если поведение изменено **намеренно** (физика, цены рун, генерация): `tools/update_golden.sh` (= `FLUX_UPDATE_GOLDEN=1 SpellSimTests -tc="Golden*"`),
затем коммит эталонов вместе с изменением — в диффе видно, что поведение изменилось сознательно. Сообщение при расхождении называет разошедшиеся
подсистемы и подсказывает команду.

## 2. Именованные хеши подсистем

`Replay::StateHashes` — до 8 пар «имя — значение» вместо трёх безымянных чисел. `SpellSim::hashes()`: `terrain`, `mana`, `characters`, `spells`,
`rng`, `tick`. При расхождении `Verdict::differing`, `describe(verdict)` и `diff(a, b)` называют подсистему («разошлись подсистемы: mana»);
дамп `FlightRecorder` содержит имена. Тест на чувствительность: один лишний прыжок на тике 1700 меняет именно `characters`.
Старые файлы читаются: их хеши называются `h0`…`h2`.

## 3. Записи повторов — журнал EventLog

Файл `--record` теперь журнал с избыточностью (полосы 4 + 2 по 256 байт): meta (сид), схемы команд, команды, трейлер (число тиков и хеши).
- **Потоковая запись:** команды пишутся по ходу игры, сброс на диск раз в секунду симуляции — при падении теряется не больше секунды.
- **Оборванная запись** (нет трейлера) читается: `complete = false`, повтор идёт до последней команды, сверять нечего (`Verdict::checked = false`).
- **Порча блоков** (≤ 2 в полосе) восстанавливается при чтении; `Recording::repair_file` / `ReplayTool repair` переписывает файл на месте.
- **Потеря команд сверх избыточности** — `Recording::load` отказывает («повтор невозможен»): молча разошедшийся повтор хуже ошибки.
  `load_with_info` отдаёт остаток и отчёт, `ReplayTool inspect` показывает, что повреждено.
- Файлы версий 1 и 2 читаются. API: `Session::record` теперь возвращает `expected` (файл создаётся сразу).

## 4. Эксперимент: мир как «сид + журнал правок» — `Sandbox/world_journal`

Консольная программа сравнивает три способа сохранить один мир (всё через EventLog; в Terrain добавлены `load_chunk` и `modified`).
Результаты (4000 правок, мир 128×64×128 м, 256 чанков, 24,0 МиБ):

| | размер | загрузка |
|---|---|---|
| полный дамп всех чанков | 24,0 МиБ | — |
| **журнал правок** (сид + 4000 событий, с чётностью) | **321 КиБ (1,3 %)** | 628 мс (генерация + повтор правок) |
| снимок 97 из 256 чанков + хвост 1000 правок | 11,4 МиБ + хвост | 197 мс |

Мир, загруженный любым способом, **побитово совпал** с исходным (хеш).

**Выводы эксперимента**
1. Журнал правок на два порядка меньше дампа и точен. Для типичной игры этого достаточно; время загрузки растёт с числом правок
   (≈ 0,16 мс на правку) — поэтому нужны контрольные точки.
2. **Снимок выигрывает только при локальных правках** (игрок работает на участках: затронуто 99 из 256 чанков). При правках по всему
   миру (`--scatter`) затронуто 250 из 256 чанков и снимок с чётностью (29 МиБ) **больше дампа** — тогда лучше полагаться на журнал.
   Следствие для дизайна: снимок делать по чанкам *по требованию* (при выгрузке чанка), а не «всё изменённое сразу».
3. **Повреждения.** До двух испорченных блоков в каждой полосе — мир восстанавливается без потерь. Потеря целой полосы журнала:
   читатель честно называет пропавшие правки (№70…№211), мир без них отличается — подмены нет. **Снимок делает потерю в начале журнала
   безвредной** (хвост после контрольной точки цел) — контрольные точки полезны и как защита, а не только как ускорение загрузки.
4. Побочное: 4000 правок по 0,13 мс = стоимость `carve_sphere` — основная часть времени загрузки; ускорить можно только пакетной
   перестройкой (применять правки без пересчёта хеша и очереди сеток до конца загрузки).

Что взять в дизайн сохранений: журнал правок как основной формат + снимки отдельных чанков при выгрузке (с номером правки, после
которой они актуальны) + периодическая проверка/ремонт файла; сид и версия генератора — в заголовок сохранения (смена генерации
ломает «сид + правки» — нужна версия `ChunkSource`).
