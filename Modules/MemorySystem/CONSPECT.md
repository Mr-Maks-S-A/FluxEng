# MemorySystem — конспект для изучения и переписывания

Читается вместе с кодом: `src/include/MemorySystem/` (7 заголовков) и `src/code/` (`Arena.cpp`, `VirtualMemory.cpp`, `Tags.cpp`) — всего около 990 строк. Зависимостей нет (только стандартная библиотека и системные вызовы).

## 1. Зачем модуль и главная идея

Память, которую симуляция и движок выделяют сотнями объектов за тик, не должна идти через `new`/`malloc`: это медленно, фрагментирует кучу и усложняет детерминизм. Здесь три основы:

1. **ZII — Zero Is Initialization.** Любой выданный блок — **нулевой**, а нулевой объект должен быть корректным «пустым» объектом. Конструкторы не нужны, инициализация бесплатна.
2. **Арена** (bump allocator): выделение — сдвиг указателя; освобождение — только целиком или откатом к отметке. Отдельного `free` нет, значит нет утечек и фрагментации.
3. **Резерв, а не выделение:** арена резервирует **виртуальные адреса** сразу (например 256 МиБ), а физическую память подтверждает по мере роста. Адреса никогда не «переезжают» (в отличие от `std::vector`), указатели в арену живут до отката.

Плюс учёт: каждая арена несёт **тег** (`Engine`, `Events`, `ECS`…), и `memory_report()` показывает, сколько физической памяти держит каждая подсистема.

## 3. Как устроено

### 3.1 `ZeroInitializable`
Концепт: trivially copyable + trivially destructible + не абстрактный + скаляр/класс/массив. Компилятор проверяет «это просто байты», но **смысл нуля** — на авторе типа: `Handle{}` — «нет объекта», счётчик `0` — «пусто».
`start_lifetime_as_array<T>` — замена `std::start_lifetime_as_array` из C++23: `memmove(p, p, n)` на себя с `std::launder`. `memmove` неявно создаёт объекты implicit-lifetime типов, а в Release вызов выбрасывается — ноль инструкций. Это нужно, чтобы работа с «сырыми» байтами арены не была UB.

### 3.2 `VirtualRegion`
- `reserve(bytes)`: размер округляется до гранулярности (на POSIX — страница); POSIX: `mmap(PROT_NONE, MAP_NORESERVE)`, то есть адреса есть, доступа нет, памяти не занято.
- `commit(offset, bytes)`: все страницы, которые задевает диапазон, → `mprotect(READ|WRITE)`. Страницы приходят **нулевыми** (анонимное отображение).
- `decommit`: освобождает только страницы, **целиком** лежащие в диапазоне; POSIX: `madvise(MADV_DONTNEED)` + `PROT_NONE`. После повторного commit страницы снова нулевые — это и держит инвариант ZII при `shrink`.
- Move-only; пустой регион валиден (`data() == nullptr`).

### 3.3 `Arena` — инвариант
> Байты от `m_position` до `m_committed` **всегда равны нулю.**

Отсюда:
- `push` **ничего не зануляет** — только выравнивание и сдвиг `m_position`. Если конец выходит за `m_committed`, `grow_commit` подтверждает ещё страниц (шаг `commit_step`, по умолчанию 64 КиБ, округлённый до страницы, но не выше `capacity`).
- `pop_to(marker)` **зануляет** освобождённый участок (`memset`) — платим один раз, и только за использованное. `reset()` = `pop_to({})`.
- `shrink()` возвращает ОС память выше текущей позиции (только для `reserve()`-арены).
- Выравнивание считается по **абсолютному адресу** (`base + position`), а не по смещению: поэтому `over(буфер)` с невыровненным началом тоже работает.
- Два источника: `reserve(capacity, step, tag)` — виртуальный резерв (растёт); `over(span)` — чужой буфер (не растёт, зануляется один раз при создании, в теги не попадает: `m_tracked = false`).
- Переполнение/ошибка ОС → `nullptr` (не исключение). Пустая арена (по умолчанию) валидна: любой `push` → `nullptr`.
- `push<T>()` / `push_array<T>(n)` — типизированные, только для `ZeroInitializable`; при неудаче `nullptr` / пустой `span`.
- Не потокобезопасна: **одна арена — один поток**. Параллельность в проекте решается тем, что у каждого потока JobSystem своя арена.

### 3.4 `ArenaScope` и `DoubleArena`
- `ArenaScope` — RAII-отметка: в деструкторе `pop_to`. Идиома «временная память функции».
- `DoubleArena` — две арены, меняются местами каждый тик (`swap` очищает новую текущую). То, что выделено в тике N в `current()`, читается в тике N+1 через `previous()` и умирает при следующем `swap`. Так устроены память тика у `Runtime` и «ответ на запрос на следующий тик» в шине событий.

### 3.5 `ArenaResource`
Адаптер к `std::pmr`: `do_allocate` → `arena.push` (при `nullptr` бросает `bad_alloc`), `do_deallocate` — пустая операция. Контейнер, который растёт в арене, оставляет «хвосты» старых буферов — нормально для временных данных; для долгоживущих лучше заранее `reserve()` контейнера.

### 3.6 `Pool<T>`
- Блок = `max(sizeof(T), sizeof(void*))` с выравниванием; блоки берутся из **собственной** виртуальной арены (адреса стабильны).
- Свободные блоки хранятся в односвязном списке **внутри себя**: на `free` блок зануляется, затем в его начало кладётся `FreeNode{next}`; на `allocate` `FreeNode` зануляется. Выдаваемый объект всегда полностью нулевой.
- `allocate()` сначала берёт из списка, потом из арены (пока `m_allocated < capacity`). `nullptr`, если пул исчерпан. `free(nullptr)` допустим. `assert(owns(item))` ловит чужой указатель в Debug.
- Двойное освобождение **не обнаруживается** (в списке окажется цикл) — ответственность вызывающего.

### 3.7 Теги
Таблица атомарных счётчиков на `MemoryTag` (`committed`, `peak`, `regions`); обновляется только при commit/decommit и создании/уничтожении арены — не на каждом `push`, поэтому дёшево. Учитывается **подтверждённая** память (то, что реально в ОЗУ). `std::vector` и прочие контейнеры сюда не попадают (нужен тегированный `pmr`-ресурс — идея из конспекта 8).

## 4. Как использовать

```cpp
using namespace MemorySystem;
Arena scratch = Arena::reserve(MiB(64), KiB(64), MemoryTag::Scratch);

Particle* p = scratch.push<Particle>();              // нулевая частица
std::span<Vec2> pts = scratch.push_array<Vec2>(1024);

{ ArenaScope s(scratch);                              // временная память
  auto tmp = scratch.push_array<int>(4096);
}                                                      // откат + зануление

auto bullets = Pool<Bullet>::reserve(10'000, KiB(64), MemoryTag::Game);
Bullet* b = bullets.allocate();  /* ... */ bullets.free(b);

ArenaResource res(scratch);
std::pmr::vector<int> visible(&res);

std::print("{}", memory_report());                    // таблица по тегам
```

Где это в проекте: `RuntimeSystem` держит `tick_arena()` (DoubleArena) и `frame_arena()`; `JobSystem` — арена на поток; `Terrain`, `ECSSystem` и др. берут `Arena`/`Pool` с тегами.

## 5. Что менять осторожно

- **Инвариант ZII** — сердце модуля. Любая новая операция обязана сохранять «хвост нулевой»: если добавляешь способ освободить память (например, `pop_to` без `memset` ради скорости), весь код, который читает свежую память, перестаёт быть корректным.
- **Move арены:** деструктор вызывает `untrack` (вычитает `m_committed` из тега). При переносе нужно переносить и `m_tracked`, и `m_committed` — иначе счётчики поплывут. Если добавишь поле, добавь его в обе операции перемещения.
- `commit_step` округляется до страницы; `capacity` — до гранулярности резерва, поэтому `capacity()` может быть чуть больше запрошенного.
- Для `Pool<T>`: при `T` с `sizeof < 8` блок больше объекта; `block_size` — публичная константа, её используют тесты.
- Теги: добавляя `MemoryTag`, обнови `to_string` и порядок до `Count`.

## 6. Упражнения для переписывания

1. Сделай арену **без** виртуальной памяти (один `new[]` на старте) и сравни `commit`-логику; что теряется (рост без переезда, теги по commit)?
2. Добавь в `Pool` обнаружение двойного `free` (например, бит «свободен» в заголовке блока) и посмотри, как это ломает ZII-«чистоту» блока.
3. Реализуй `ArenaStats` для `DoubleArena` и выведи пик за тик — где арена тика реально упирается?
