# Конспект 100 — полосы событий: быстрые, предсказуемые, отслеживаемые (2026-10-13)

Это запись **идеи**, а не отчёт о сделанном: код не менялся. Источник — беседа о шине событий; плюс разбор того, что в `EventSystem`, `EventLog`, `Phases` уже есть и что оттуда стоит забрать.

## 1. Цель

Приоритеты автора: **скорость** (события не стопорятся в обработке) и **точность** (зависимости видны сразу, проблема локализуется легко). Пример-критерий: ошибка из коллизии не может попасть в рендерер, а если попала — её путь прослеживается за минуты.

## 2. Идея: полосы доставки

Аналогия с транспортом: классы различаются не размером сообщения, а двумя вещами — **кто владеет памятью** и **когда потребитель читает**.

| Полоса | Что | Когда видно | Пример |
|---|---|---|---|
| Байк | одно сообщение, прямой вызов | сразу, в контексте отправителя | сброс ввода, «сущность умерла» (с бюджетом) |
| Авто | очередь типизированных событий | в начале следующей фазы/тика, по порядку | «снаряд попал», «дверь открыта» |
| Автобус | пакет однородных записей (SoA, `span`) | раз за тик, читатель идёт по массиву | список контактов, видимые объекты |
| Поезд | целый снимок состояния, двойной буфер | раз в кадр / в сетевой пакет / в запись | кадр для рендера, реплей, сеть |

Вопрос «как отправить X» превращается в «к какой полосе X относится» — по частоте и количеству, а не по важности.

## 3. Правила скорости (чтобы ничто не стопорилось)

1. **Pull, а не push.** Производитель только пишет в буфер и идёт дальше. Обработчик не выполняется в контексте отправителя — иначе медленный получатель останавливает физику.
2. **Без выделений и замков внутри тика.** Буферы фиксированной ёмкости создаются заранее.
3. **Жёсткая ёмкость и явное переполнение.** Не молчаливый рост очереди: счётчик потерь + громкая ошибка в отладке.
4. **Одна точка синхронизации — барьер между фазами.** Канал пишется в фазе N, читается в N+1; внутри фазы писатель и читатель не касаются одной памяти.
5. **Задержка — ровно одна фаза/тик, везде одинаково.** Это принятая цена pull-модели, но предсказуемая.
6. «Байк» — только для дешёвого и обязательного немедленно, и с бюджетом, иначе он вырождается в скрытую цепочку.

## 4. Правила точности (чтобы проблему находили быстро)

1. **Граф зависимостей — данные.** Для канала указан производитель и читатели. По нему строится граф и проверяется сборка: рендерер, читающий `ContactBatch`, — ошибка, а не предупреждение.
2. **Недоступность по типу.** Контракты (заголовки событий) лежат отдельно от модулей; у рендерера в зависимостях нет заголовка контактов, поэтому он не может даже назвать тип. Ловится на сборке, а не в рантайме.
3. **Поток однонаправленный:** симуляция → представление. Назад идут только команды (в проекте они уже единственный вход в мир). Представление не может влиять на симуляцию.
4. **След — это данные.** Запись несёт происхождение (производитель, тик, порядковый номер); на канал — кольцо последних N записей в отладке. Вопросы «кто записал / что / когда прочитали» разбираются без воспроизведения бага.
5. **Детерминированный порядок.** Производители в фазе идут в фиксированном порядке; при параллельности — сортировка по ключу.

## 5. Одно объявление на канал

Скорость, граф и трассировка должны выводиться из **одного** описания: тип записи, производитель, читатели, ёмкость, полоса, фаза записи и чтения. Читать канал может только тот, кто в описании.

## 6. Что уже есть и что можно забрать

Разбор по коду (`Modules/EventSystem`, ~2650 строк заголовков, 14 файлов тестов, `compile_fail`, бенчмарки).

### 6.1. Уже реализовано и совпадает с идеей

| Идея | Что в коде | Оценка |
|---|---|---|
| Pull, одна фаза задержки | `Stream`: отправленное в тике N видно в N+1, двойной буфер, `swap` O(1) | **забрать как есть** — это ядро |
| Горячий путь без виртуальных вызовов | `EventWriter`/`EventReader` держат указатель на буфер навсегда | забрать |
| Явное переполнение | `max_events_per_tick`, `emit` → `false`, `total_dropped`, `peak_per_tick` | забрать; добавить «громко в отладке» |
| Параллельная запись без замков | дорожки потоков, слияние по номеру → одинаково при любом числе потоков | забрать (уже «автобус» для параллели) |
| Автобус как SoA | `Layout::SoA`, `column<&E::f>()` | это и есть полоса «пакет» |
| Объединение и отложенные | `Coalesced`, `Scheduled` (`emit_after`) | забрать; закрывает «dirty-флаги» и таймеры |
| Граф зависимостей | `declare_module().produces<>().consumes<>()`, `EventGraph`: `to_dot`, `orphan_events`, `module_order` | забрать; это пункт 4.1 |
| Проверка контракта | `writer<E>(module)`, `reader<E>(module)` бросают, если не объявлено | забрать, но см. 6.2 |
| След | `trace`, `EventRef`, `cause_chain`, кольцевой журнал 65 536 | забрать; это пункт 4.4 (частично) |
| Фазы | `Phases::Schedule`: именованные фазы, замер времени, `set_enabled` | основа для «барьер между фазами» |
| Домены времени | `Domain::Tick` / `Frame` (кадровые живут и на паузе) | основа для разделения «симуляция / представление» |
| Запись и восстановление | `EventLog`: журнал с CRC, чётностью Рида—Соломона, `BusAdapter::record/Replayer` | основа полосы «поезд» для реплея и аварийного разбора |

### 6.2. Расхождения и дыры (честно)

1. **Шиной почти никто не пользуется.** Объявляют модули только `Core::App` (клавиши, мышь) и `SpellSim` (одно событие `TerrainEditedEvent`). Реальные потоки проекта — **команды** (`Replay::Command`, `Net::Lockstep`) и прямые вызовы — идут мимо шины. Значит граф зависимостей сейчас почти пуст и ничего не доказывает.
2. **Контракт не обязателен.** `writer<E>()` и `reader<E>()` без модуля работают в обход проверки. Для правила 4.1 «читает только объявивший» нужен только вариант с `ModuleId`.
3. **Нет проверки на сборке.** `tools/check_modules.sh` проверяет самостоятельность модулей (CMake), но не «рендерер не видит контакты». Нужно отдельное правило: список разрешённых контрактов на модуль.
4. **Нет полосы «поезд».** Снимок для рендера/сети/реплея в шине не выражен; сейчас каждый делает свой (`WorldRender`, `Net` blob, `Replay`).
5. **Нет полосы «байк».** Мгновенной доставки нет — и это хорошо для детерминизма; её надо вводить только осознанно и вне состояния симуляции.
6. **Трассировка линейная.** `cause_chain` — поиск по журналу; годится для отладки, как и сказано в конспекте модуля.
7. **Лимиты `EventRef`:** 12 бит канала (≤ 4096), 20 бит индекса (≤ ~1 млн/тик) — превышение молча обрезается маской.
8. **Шина не потокобезопасна.** Параллельность только через дорожки; для поезда-снимка между потоками нужен отдельный механизм.

### 6.3. Что ещё стоит забрать из соседних модулей

- **`Phases::Schedule`** — барьер между фазами как данные; сейчас им пользуется только `SpellSim`. Чтобы канал был привязан к фазе («пишется в `physics`, читается в `render`»), расписание и шина должны знать друг друга.
- **`EventLog`** — готовый «чёрный ящик»: при ошибке в отладке можно писать последние N тиков событий шины и разбирать после.
- **Команды** — уже «единственный вход в мир»; они же — обратная сторона правила 4.3. Не смешивать с событиями: команда — вход симуляции, событие — выход.

## 7. Предлагаемый порядок работ

1. **Подключить к шине реальный поток.** Выбрать один путь (например, «магия → видимые эффекты» из `SpellSim`) и пустить его через канал с контрактом. Пока граф пуст, остальное — теория.
2. **Сделать контрактные ручки обязательными** (`writer(ModuleId)`/`reader(ModuleId)`), а голые версии — только для тестов.
3. **Правило на сборке:** файл `contracts.txt` (или в CMake): какие события модуль вправе объявлять; `check_modules.sh` падает при нарушении. Закрывает «коллизия → рендерер».
4. **Привязать канал к фазе** (`Phases` + `EventSystem`): объявление «пишется в фазе X, читается в Y»; проверка, что Y строго после X.
5. **Полоса-снимок** (поезд): один двойной буфер `Snapshot<T>` для рендера, сети и реплея — сначала посмотреть, чем отличаются сегодняшние три копии.
6. **Отладочное кольцо на канал** (последние N записей с происхождением) и вывод графа `--events-graph`.

## 8. Открытые вопросы

1. Нужны ли события **внутри** симуляции (между модулями) или только на выходе? Если внутри — они входят в хеш и порядок обязателен; если только на выходе — всё проще.
2. Куда в первую очередь идёт «поезд»: рендер, сеть или реплей? Скорее всего это один снимок.
3. Нужна ли параллельность внутри тика каналам уже сейчас? От этого зависит сложность первого варианта.
4. Допустимо ли «байк» вообще, или все реакции — минимум на фазу позже (проще для детерминизма)?

## 9. Что нельзя ломать

- Единая модель времени: «видно в N+1»; цепочка реакций не может зациклить тик (важно для заклинаний игроков).
- Горячий путь без виртуальных вызовов и замков.
- Формат `EventId = FNV-1a(event_name)` и формат `EventLog` (версия файла, golden-эталоны).
- Детерминизм: порядок слияния дорожек и сортировка — часть результата.
