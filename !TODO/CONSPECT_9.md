# Конспект 9. Система событий: один канал на все политики, дорожки потоков без мьютексов, домены, дерево причин

> Задача: улучшить EventSystem и выяснить, были ли локальные очереди для потоков. **Не были**: в Siege
> параллельные системы писали события во внешние `JobSystem::ChunkBuffers` (вектора структур, то есть AoS),
> а потом главный поток по одному перекладывал их в шину. Шина сама была однопоточной.
> Требование: **без мьютексов и с сохранением SoA**. Сделано.

---

## 1. Что было и что мешало

| Было | Почему мешало |
|---|---|
| Одна политика `Stream`; `StreamChannel` — единственная реализация `IChannel` | новая политика = новый класс канала, а писатель/читатель знали конкретный класс |
| Шина однопоточная | параллельные системы обходили шину через `ChunkBuffers` — SoA терялось, лишнее копирование |
| Одно время — тики | интерфейс и ввод на паузе (нет тиков) «замирали» вместе с симуляцией |
| Причин событий нет | «почему этот юнит умер?» — только логами |

Главный ограничитель (о нём был прошлый разговор): **писатель и читатель были привязаны к реализации
политики**. Пока это так, каждая новая политика тянет за собой переписывание горячего пути. Поэтому
первым шагом всё свёл в один класс.

## 2. Один `Channel` для всех политик

```
 emit()  ─────────────▶ pending ──┐
 дорожки 0..N ─▶ lanes[i] ────────┤ advance(): 1) слить дорожки в pending (по порядку, бюджет)
                                  │             2) политика решает, что попадёт в ready
 читатели ◀──────────── ready ◀───┘
```

Горячий путь (`emit`, чтение) **одинаков для всех политик** — `push` в `pending`, чтение из `ready`.
Политика живёт только в `advance()`:

| Политика | `advance()` | Пример |
|---|---|---|
| `Stream` | `swap(ready, pending)` — O(1) | попадания, столкновения |
| `Coalesced` | одно событие на ключ: последнее значение **на месте первого** (порядок стабилен) | «здоровье изменилось» — UI нужно последнее значение |
| `Scheduled` | `emit_after(e, delay)`: созревшие отложенные (они старше) → затем обычные | яд, перезарядка, отрастание деревьев |

- `emit(e)` в Scheduled — это `emit_after(e, 1)`. Задержка 0 поднимается до 1: «сейчас» в шине не бывает,
  иначе реакция могла бы зациклить тик.
- Ключ Coalesced — поле до 8 байт, выбирается `coalesce_key<E, &E::field>()` (проверка при компиляции, что поле
  принадлежит событию). SoA-события сливаются тоже — колонки остаются колонками.
- `StreamChannel` теперь просто `using StreamChannel = Channel;` — старый код не сломан.
- Политику и домен канала **нельзя сменить** после создания (исключение): у читателей уже есть ожидания.

## 3. Дорожки потоков (lanes) — ответ на главный вопрос

### Как пользоваться

```cpp
auto lanes = writer.lanes(js::chunk_count(count, grain));       // главный поток, ДО работы
js::parallel_for(jobs, count, grain, [&](size_t b, size_t e, size_t chunk) {
    for (size_t i = b; i < e; ++i)
        if (hit(i)) lanes.emit(chunk, Hit{...});                 // без мьютексов и атомиков
});
fired += lanes.total();                                          // после работы — можно считать
// bus.advance_tick(): дорожки слились в порядке номеров
```

### Почему нет мьютексов и это безопасно

1. **Одна дорожка — один писатель.** Дорожка привязана к куску работы (`chunk`), а кусок выполняет ровно
   один поток. Делить нечего, значит и синхронизировать нечего.
2. **Дорожки создаются заранее**, в главном потоке (`lanes(count)` → `open_lanes`). Во время работы вектор
   дорожек не растёт — указатели не плывут.
3. **`alignas(64)` на каждую дорожку** — своя кэш-линия. Без этого счётчики `size` соседних дорожек лежали бы
   в одной линии, и потоки «толкались» бы (false sharing) — не ошибка, но тормоза.
4. **Слияние — в главном потоке**, после `parallel_for` (он ждёт все куски — это и есть точка синхронизации,
   happens-before даёт сам планировщик).
5. Проверено **ThreadSanitizer**: тест с 8 настоящими `std::thread` — гонок нет.

### Почему SoA сохраняется

Дорожка — это **обычный `EventBuffer` той же схемы и раскладки**. У SoA-события в дорожке те же колонки
(`x[]`, `y[]`, `z[]`…), что в основном буфере. Слияние — `EventBuffer::append`: **один `memcpy` на колонку**,
а не по событию. Читатель после тика видит непрерывные колонки, как будто писал один поток.

### Почему результат детерминирован

Порядок после слияния: **сначала события главного потока, затем дорожки в порядке номеров** (и в порядке
открытия, если несколько систем открыли дорожки в одном тике). Какой поток какой кусок взял и когда — не важно.
Тест: 100 000 элементов, 1 поток против 8 — колонки побайтно равны. Siege: контрольная сумма
`3de10b3e24aea3bf` одинакова при `--threads 0` и `--threads 7`.

### Бюджет

`max_events_per_tick` нельзя проверять в дорожках: это был бы общий счётчик (атомик) и порядок отбрасывания
зависел бы от гонки потоков. Поэтому **бюджет применяется при слиянии**: дорожки идут по порядку, лишнее
отбрасывается с конца — тоже детерминированно, считается в `total_dropped`.

### Цифры (Release, 16 ядер, 1M SoA-событий по 32 байта)

| Сценарий | Время | |
|---|---|---|
| обычный `emit`, 1 поток, событие на каждый элемент | 3.7 мс | эталон |
| дорожки, 1 / 4 / 8 потоков, только запись | 10.0 / 5.7 / 5.4 мс | **упирается в память** |
| работа + событие у 1/8 элементов, обычный `emit` | 21.6 мс | |
| то же, дорожки 1 / 4 / 8 потоков | 24.2 / 6.4 / **3.7 мс** | **×5.8** |

Вывод: когда система только пишет события (без вычислений), дорожки проигрывают — каждое событие пишется
дважды (в дорожку и при слиянии). В настоящих системах событие — редкий результат большой работы
(проверка попаданий, навигация), и тогда масштабирование почти линейное.

## 4. Домены времени: Tick и Frame

`ChannelConfig::domain`. Каналы `Tick` двигает `advance_tick()` (фиксированный шаг симуляции), каналы `Frame` —
`advance_frame()` (каждый кадр). Core теперь вызывает `advance_frame()` каждый кадр.

Зачем: на паузе тиков нет, но интерфейс, ввод, отладочные события должны жить. И наоборот: при 3 тиках
за кадр событие UI не должно «прожить» 3 тика.

## 5. Дерево причин (ответ на «древовидную иерархию событий»)

```cpp
bus.register_event<Damage>({.trace = true});
damage.emit(Damage{...}, collisions_in.ref(i));   // «урон из-за этого столкновения»
bus.trace_tree(root);
// test.collision@1#1
//   test.damage@2#0
//     test.heal@3#0
```

- `EventRef` — 64 бита: `(момент + 1) << 32 | канал (12 бит) << 20 | индекс (20 бит)`. Ноль = «нет причины».
- Ссылка **вычисляется из позиции**, а не из глобального счётчика — значит одинакова в повторах и при любом
  числе потоков (через дорожки причина тоже проходит: `lanes.emit(chunk, e, cause)`).
- Шина пишет кольцевой журнал (`set_trace_capacity`, по умолчанию 65 536 записей): `cause_chain` (вверх к корню),
  `effects` (вниз), `trace_tree` (текст).
- Каналы без `trace` не платят ничего — нет даже вектора причин.
- Coalesced сохраняет причину **победившего** (последнего) события — остальные исчезли вместе с событиями.

Это дерево — не иерархия типов событий («Damage наследует Combat»), а иерархия **конкретных случаев**. Именно
такая нужна при отладке: «почему сработало?» — а не «к какой категории относится?».

## 7. Правила (запомнить)

1. `lanes()`, `register_*`, `advance_*` — **только главный поток**. Параллельно — только `lanes.emit`.
2. Одна дорожка — один поток. Номер дорожки = номер куска, не номер потока (номер потока недетерминирован).
3. Дорожки живут до ближайшей смены момента канала.
4. Не проверяй бюджет и не считай события в дорожках через общий счётчик — посчитай `lanes.total()` после работы.
5. Политика выбирается по тому, **что нужно читателю**: все случаи (Stream), последнее состояние (Coalesced),
   «потом» (Scheduled).

## 8. Что дальше (для финальной версии)

- **Слияние без копии.** Двухпроходная схема: потоки сначала считают события по кускам, затем префиксная сумма
  даёт каждому куску его место прямо в `pending`, и потоки пишут туда. Копии нет, но нужно два прохода — выгодно
  только для «только запись». Альтернатива — читатель, который видит дорожки сегментами (колонки перестают быть
  одним span'ом).
- **Ввод в домене Frame**: перевести `KeyEvent`/`MouseButtonEvent` в Core на кадровые каналы, чтобы ввод на паузе
  доходил до UI.
- **Причины в отладочном UI**: клик по сущности → `trace_tree` последнего события о ней.
- **Ограничения `EventRef`**: 4096 каналов и ~1M событий на канал за момент. Для финала — либо шире (128 бит),
  либо явная проверка при регистрации/слиянии.
- **Сеть и повторы**: детерминированный порядок слияния и `EventRef` из позиции — готовая основа для записи
  ввода и сравнения прогонов.
