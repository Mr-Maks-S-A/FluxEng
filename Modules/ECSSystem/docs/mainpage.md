# ECSSystem — ECS FluxEng {#mainpage}

ECSSystem хранит **состояние мира**: сущности и их компоненты. Это пара к EventSystem:
события сообщают, *что случилось*, компоненты хранят, *как есть сейчас*.
Подключение: `#include <ECSSystem/ECSSystem.hpp>`, CMake-цель `engine::ECSSystem` (header-only).

## Сущность — ссылка с поколением

ECS::Entity — это `{index, generation}`, 8 байт. Слот переиспользуется после смерти,
а поколение растёт, поэтому старые ссылки перестают совпадать:

```
create()               → {5, gen 1}
destroy({5, 1})          слот 5 свободен
create()               → {5, gen 2}      тот же слот
world.valid({5, 1})    → false           ссылка «видит», что сущность умерла
world.get<T>({5, 1})   → nullptr         и не попадёт в компонент новой
```

Это ровно проблема, которую Ecosystem в Sandbox решает вручную (`Handle` + Life):
лиса отправила охоту в тике N, а к тику N+1 заяц умер и его слот занят.

**ZII.** `Entity{}` = «нет сущности»: слот 0 никогда не выдаётся, у живых поколение ≥ 1.
Компонент `Target { ECS::Entity entity; }` по умолчанию означает «цели нет» без отдельного флага.

## Хранение: sparse set со страницами

```
sparse (по слоту, страницами по 4096):   [ 0 | 3 | 0 | 1 | 2 | 0 … ]   0 = нет компонента
dense entities:                           [ e3 | e4 | e1 ]
dense components:                         [ c3 | c4 | c1 ]            ← системы идут здесь
```

- emplace / get / remove — O(1); удаление переставляет последний элемент на место удалённого.
- Страницы создаются по требованию и **обнулены** — ноль значит «компонента нет» (ZII),
  поэтому новая страница не требует инициализации.
- Предела числа сущностей нет. В прошлой версии был `MAX_ENTITIES = 10000` и массивы
  фиксированного размера в каждом пуле (~200 КБ на тип компонента даже без сущностей).

## Выборки

```cpp
world.view<Position, const Velocity>().each([](Position& p, const Velocity& v) {
    p.x += v.x;
});
world.view<Health>().each([&](ECS::Entity e, Health& h) {
    if (h.value <= 0) world.destroy(e);   // удалять ТЕКУЩУЮ сущность можно
});
```

- Обход идёт по **наименьшему** пулу выборки: `view<Position, Burning>` при 100 000 Position
  и 1 000 Burning пройдёт 1 000 сущностей.
- `const T` в выборке — доступ только на чтение.
- Обход с конца: удаление текущей сущности безопасно. Добавлять компоненты и удалять
  **другие** сущности во время обхода нельзя — соберите их в список и примените после
  (см. @ref 03_systems.cpp).

## Замеры (GCC 14, RelWithDebInfo, x86-64)

| Замер | ECS | «Голые» `std::vector` |
|---|---|---|
| обход 1 компонента, 100 000 | ~1.4 млрд/с | ~3–4 млрд/с (векторизуется) |
| обход 2 компонентов у всех, 100 000 | ~0.47 млрд/с | ~2.3 млрд/с |
| обход 2 компонентов, пересечение 1% из 100 000 | 1 000 сущностей за ~3 мкс | — |
| get по случайной сущности | ~6 нс | — |
| destroy + create + 2 компонента | ~73 нс | — |

Разрыв с «голыми» массивами — цена гибкости: второй компонент ищется в своём пуле
(страница → индекс → сверка сущности). Когда он станет узким местом, следующий шаг —
«группы» (владеющие выборки), где пулы держат общие сущности в одинаковом порядке.

## Чего здесь нет (пока)

- Многопоточных систем: World не потокобезопасен.
- Групп и сортировки пулов.
- Сериализации: `component_id<T>()` не стабилен между запусками, для сохранений нужен ID по имени типа.
