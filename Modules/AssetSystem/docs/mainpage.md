# AssetSystem — ассеты на стороне процессора {#mainpage}

AssetSystem превращает файлы (PNG/JPG/BMP, glTF/GLB, JSON, любые байты) в данные в памяти: загружает в фоне,
кеширует, проверяет лимиты и **не знает ни про окно, ни про GPU** — поэтому его использует и клиент, и выделенный сервер.
GPU-ресурсы клиент создаёт сам, в главном потоке, из обратного вызова `on_done`.
Подключение: `#include <AssetSystem/AssetSystem.hpp>`, цель `engine::AssetSystem`. Зависимости: JobSystem; stb_image и cgltf — внутри.

## Путь ассета

```
 исходники            cook (при сборке)         рантайм игры
 model.gltf + .bin ─► AssetSystem::cook_directory ─► pack.fxpk ─► PackSource ─┐
 texture.png ───────────────────────────────────────────────────────────────┤  VirtualFileSystem
 spells.json ───────────────────────────────────────────────────────────────┘  (память | каталог | пак, позже смонтированное перекрывает)
                                                                                   │
                                          AssetManager::load<T>(path) ─ кеш ─ JobSystem ─ загрузчик ─ Handle<T>
                                                                                   │ on_done / pump() — в главном потоке
                                                                                   ▼
                                                                               GPU-ресурсы
```

| Часть | Что делает |
|---|---|
| AssetSystem::normalize_path, AssetSystem::AssetId | один путь — один вид и один стабильный 64-битный id (FNV-1a); `..`, `:`, управляющие символы — ошибка |
| AssetSystem::VirtualFileSystem + источники | память, каталог (не выходит за корень даже через симлинк), пак; поздний источник перекрывает ранний — так работают моды |
| AssetSystem::PackWriter / AssetSystem::PackSource | пак `.fxpk` с CRC-32 каждой записи, воспроизводимая сборка |
| AssetSystem::decode_image | stb_image; размеры проверяются по заголовку **до** выделения памяти |
| AssetSystem::parse_gltf | cgltf; внешние буферы читаются через VFS; узлы склеены, преобразования применены, нормали достроены |
| AssetSystem::serialize_mesh / AssetSystem::parse_mesh_binary | собственный формат `.fmesh` с CRC-32 |
| AssetSystem::cook_directory | glTF → `.fmesh`, остальное копируется; консольная утилита `flux_cook <каталог> <выход.fxpk>` |
| AssetSystem::AssetManager | кеш, фоновая загрузка, `on_done` + `pump()`, `evict()` для перезагрузки, статистика |

## Правила менеджера

- **Один путь — одна загрузка.** Пока ассет жив, `load<T>(path)` возвращает тот же слот; загрузчик вызывается один раз,
  даже если просят 8 потоков одновременно.
- **Кеш слабый.** Менеджер держит `weak_ptr`; ассет живёт, пока у кого-то есть Handle. `collect()` убирает умершие записи.
- **Ошибка — состояние.** Нет файла, битый файл, превышен лимит — `Handle::failed()` и `Handle::error()`; исключения не летят.
  Неудачная загрузка тоже кешируется: повторить можно через `evict<T>(path)`.
- **GPU — только в главном потоке.** Фоновые потоки читают и разбирают; всё, что трогает рендер, — в `on_done`, который
  выполняет `pump()` в вызывающем потоке.
- **Деструктор менеджера дожидается задач в полёте;** Scheduler и VFS обязаны пережить менеджер.

## Недоверенные данные

В мультиплеере вы разбираете то, что прислал сервер или мод. Поэтому: лимиты (`AssetLimits`: файл, пиксели, вершины, индексы,
записи пака); проверка индексов, границ и контрольных сумм; любая ошибка данных — `Result`, а не падение. Тесты прогоняют
усечения и случайную порчу каждого формата под ASan/UBSan.

## Чего здесь нет (сознательно)

Зависимостей между ассетами (текстура сетки загружается отдельным `load`, см. Sandbox/asset_lab), встроенных в GLB картинок,
анимаций и скелетов, сжатых текстур (KTX2/BCn), горячей перезагрузки по изменению файла (есть `evict` как основа),
аудио и шрифтов. Формат `.fmesh` и пак имеют номер версии — расширять можно без поломки старых файлов.
