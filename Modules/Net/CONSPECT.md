# Net — конспект для изучения и переписывания

`src/include/Net/{Lockstep,Transport,Wire}.hpp`, `src/code/{Lockstep,Transport,Wire}.cpp` (~810 строк). Зависит от `Math` и `Replay` (`Command`, `StateHashes`). Реального UDP нет — только интерфейс `Transport` и сеть в памяти.

## 1. Зачем и главная идея

Симуляция детерминирована → по сети идёт **ввод, а не состояние мира** (lockstep). Каждый пир:
- шлёт свои команды на тик `T + input_delay`;
- исполняет тик `T`, только когда команды **всех** пиров на него собраны; склейка идёт в порядке номеров пиров — одинаково у всех;
- сверяет **именованные хеши подсистем**; расхождение называется по тику и подсистеме.

Сеть ненадёжна (потери, задержки, перестановки, дубли, порча) — протокол строится так, чтобы это не требовало отдельных запросов: **любой следующий пакет лечит потерю предыдущих**.

## 3. Как устроено

### 3.1 Пакеты (`Wire`)
`Packet{from, variant<Hello, Inputs, BlobChunk, BlobAck, HashReport>}`; версия протокола, CRC-32C; `decode` — **граница доверия**: любая порча/обрезка → `unexpected(текст)`, не падение; пакет ≤ 1200 байт (один MTU без фрагментации). Фаззинг в тестах.
- `Hello{peer_count, seed, config_hash, knows_you}` — знакомство: сверяет число игроков, сид мира, хеш настройки (уровень + версия правил). `knows_you=false` ⇒ получатель обязан ответить, чтобы знакомство не зависло от потери пакета.
- `Inputs{acked, ticks[]}` — **все ещё не подтверждённые** тики отправителя (до бюджета `1200 − 64`) + подтверждение «у меня ваши тики `[0, acked)`».
- `BlobChunk{hash, total, offset, data}` / `BlobAck{hash}` — блобы кусками по 1000 байт.
- `HashReport{tick, hashes}` — хеши подсистем после тика.

### 3.2 `Lockstep` — цикл кадра
```
pump()                 принять пакеты, отправить/повторить свои
needs_input()?  →  submit(commands)     команды на тик tick() + input_delay
ready()?        →  sim.tick(advance())  команды ВСЕХ пиров на tick() есть (и все нужные блобы)
                   report_hashes(sim.hashes())
desync()?       →  разошлись на тике N: подсистемы …
```
Ключевые поля: `m_tick` (исполняемый), `m_local_next` (первый ещё не поданный свой тик), `m_inputs[пир][тик]`, `m_have[пир]` (тики `[0, have)` есть подряд), `m_peer_acked[пир]`.
- **Старт:** первые `input_delay` тиков **пусты у всех** (никто ещё ничего не мог подать) — иначе игра не стартует. Поэтому `m_have`/`m_peer_acked` начинаются с `input_delay`.
- `submit` кладёт команды (≤ 16) на `m_local_next`, сдвигает `m_have[local]`. `ready()` требует: связь есть, у **каждого** пира есть запись на `m_tick` и (если задан `blob_reference`) все блобы, на которые ссылаются команды этого тика. `advance()` склеивает по возрастанию номера пира, чужие записи стирает, **свои держит** до подтверждения всеми.
- `pump`: принимает датаграммы (чужие/битые/свои — `bad_packets`), стирает свои тики ниже `floor = min(m_tick, подтверждения всех)`, шлёт `Hello` (при отсутствии связи — каждые `resend_interval` pump'ов, потом раз в 32 — дёшево лечит потерю), затем `Inputs` каждому и куски блобов. Если не готов — `stalled_pumps++`.
- `Inputs` на приёме: `m_peer_acked` растёт (не выше `m_local_next`); принимаются тики в окне `[have, m_tick + 512)`; затем `have` сдвигается по непрерывному префиксу. Дубликаты и перестановки безвредны (`try_emplace`).

### 3.3 Блобы
`submit_blob(bytes)` → `content_hash`; сохраняется локально и ставится в очередь отправки каждому пиру. `send_blobs`: не более `max_blob_chunks_per_pump` (2) кусков на пира за pump, чтобы блоб не заглушил ввод; конец → снова с начала, пока не придёт `BlobAck`. Приём: `Partial{total, data, offsets, received}` (до 16 частичных); собрав все байты, **сверяет хеш**; не сошёлся — отбрасывает (`blobs_rejected`), отправитель повторит. Уже имеющийся блоб подтверждается сразу (потерялось подтверждение).
`set_blob_reference(fn)`: функция «команда → хеш блоба, который ей нужен» (`SpellSim::blob_reference`) — **ворота** `ready()`: команда `SetProgram` не исполнится, пока блоб не пришёл и не сошёлся.

### 3.4 Сверка состояния
`report_hashes` запоминает свои хеши тика `m_tick − 1` (кольцо 256), шлёт `HashReport`; пришедшие раньше своих хешей откладываются; `compare` вызывает `StateHashes::differing` и **запоминает только первое расхождение** (`Desync{tick, peer, subsystems}`) — дальше всё разойдётся.

### 3.5 `LoopbackNetwork` — плохая сеть в памяти
По сиду (`Math::Rng`): `latency_steps`, `jitter_steps` (перестановка), `loss_permille`, `duplicate_permille`, `corrupt_permille` (порча одного бита — CRC должна поймать), `set_link(...)` меняет линию на лету (обрыв связи). `step()` — шаг времени сети. Воспроизводимо: те же сид и параметры — те же потери.

## 4. Как использовать

```cpp
Net::LoopbackNetwork net_sim(2, {.latency_steps = 3, .loss_permille = 200}, /*seed*/ 7);
Net::Lockstep net(net_sim.endpoint(my_id), {.local = my_id, .peers = 2, .seed = world_seed, .config_hash = level_hash, .input_delay = 3});
net.set_blob_reference(SpellSim::blob_reference);

// каждый кадр:
net_sim.step();                       // только в тестах: реальная сеть идёт сама
net.pump();
if (net.needs_input()) net.submit(my_commands);
if (net.ready()) {
    auto cmds = net.advance();
    sim.tick(cmds);
    net.report_hashes(sim.hashes());
}
if (auto d = net.desync()) report(d->tick, d->subsystems);
const std::uint64_t h = net.submit_blob(Runes::encode_program(p));   // правка редактора; затем команда set_program_command(slot, h)
```
Где это в проекте: `Sandbox/CoopScribe` (пилот и писарь по плохой сети, читер ловится на первом тике), интеграционные тесты `Integration.cpu: …net_spellsim`. Рядом: `Replay::Command` — единица обмена; `Replay` и `Net` вместе дают «записать сетевую партию» (пока вручную).

## 5. Что менять осторожно

- **Пиры считаются честными:** подмена ввода и «мёртвый» блоб останавливают игру (`stalled_pumps`), но не карают. Нет таймаутов, исключения пира, переподключения с досылкой состояния.
- **Хеш блоба — FNV** (от случайных ошибок, не от злоумышленника).
- **Инварианты старта:** `input_delay ≥ 1` (`FLUX_ASSERT`), первые `input_delay` тиков пусты у всех. Измени одно — игра не стартует или рассинхронизируется.
- **Свои тики держатся до подтверждения всеми** (иначе нечем лечить потери); освобождение — по `floor` в `pump`.
- Окно приёма ввода `512` тиков и бюджет пакета `1200 − 64` — связаны с `max_packet_size`; при увеличении команд на тик пересчитай бюджет.
- `Hello` повторяется и после соединения — это не лишнее: оно лечит потерю подтверждения знакомства.
- Сейчас в `SpellSim` **один персонаж**: пиры управляют им совместно. Для мультиплеера нужен `player_id` в команде (`Command` ровно 16 байт — решить, расширять ли).
- Сложность кадра ~ квадрат числа пиров (пакет каждому каждый кадр): 2 пира ≈ 2 мкс, 8 пиров ≈ 46 мкс.

## 6. Упражнения для переписывания

1. Напиши `UdpTransport` (сокеты неблокирующие) и прогони `CoopScribe` по localhost — что поменялось в коде протокола? (должно: ничего).
2. Добавь таймаут и исключение пира: что делать с его будущими тиками (пустые? последние команды?) и как не расходиться с остальными?
3. Реализуй переподключение со снимком состояния: что отправлять (хеши по подсистемам уже есть, журнал `Replay` — потоковый)?
4. Сделай `player_id` частью команды и обработку нескольких персонажей в `SpellSim` — как менять `blob_reference`?
5. Добавь адаптивную задержку ввода (по измеренному RTT) и проверь, что состояние на тике N по-прежнему одинаково.
6. Сделай запись сетевой партии: `Lockstep::advance()` → `Replay::Session::begin_tick` как наблюдатель (конспект 16, п. 3.1).
