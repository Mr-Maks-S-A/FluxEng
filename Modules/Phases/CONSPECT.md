# Phases — конспект для изучения и переписывания

Самый маленький модуль: `src/include/Phases/Schedule.hpp` (83 строки) и `src/code/Schedule.cpp` (~85). Зависит только от `Math` (ради `FLUX_ASSERT`).

## 1. Зачем и главная идея

Тик симуляции — это **последовательность шагов**, и её порядок влияет на результат («сначала команды, потом заклинания, потом ландшафт»). Раньше порядок был вшит в одну большую функцию `tick`. `Schedule` делает его **данными, которые видно**: список именованных фаз.

Что это даёт:
- модуль вставляет свою фазу `insert_after("movement", "machines", fn)` и не правит чужой код;
- фазу можно выключить на лету (`set_enabled`) — отладка «а что, если мана не шагает»;
- время каждой фазы замеряется само (оверлей, профилирование).

Замеры **не попадают в состояние симуляции** — время недетерминировано, оно только для отладки.

## 2. API целиком

| Метод | Поведение |
|---|---|
| `add(name, fn)` | в конец; **повторное имя — `FLUX_ASSERT`** (нарушение контракта); возвращает `*this` — цепочка `.add().add()` |
| `insert_before(anchor, name, fn)` / `insert_after(...)` | вставка относительно якоря; `false`, если якоря нет (ничего не добавлено) |
| `remove(name)` | убрать; `false`, если нет |
| `set_enabled(name, bool)` | включить/выключить без удаления |
| `run()` | включённые фазы по порядку, замер каждой `steady_clock` |
| `names()`, `contains()`, `size()` | интроспекция |
| `times()`, `total_ms()` | время фаз последнего `run()` (выключенные — 0) |

## 3. Как устроено

- Хранилище — `std::vector<Phase>`, `Phase = {std::string name, Fn fn, bool enabled}`; поиск по имени — линейный (`find`). Фаз единицы-десятки, поэтому хеш-таблица не нужна, а порядок хранения = порядок выполнения.
- `m_times` — параллельный вектор `PhaseTime{string_view name, double ms}`; `string_view` указывает на `std::string` внутри `m_phases`. Любая вставка/удаление сдвигает строки, поэтому после неё вызывается `rebuild_times()` (пересоздаёт `string_view`). `set_enabled` порядок не меняет — перестраивать не нужно.
- Перемещение `Schedule` разрешено (буфер вектора переходит целиком, строки не двигаются, `string_view` остаются валидны), **копирование запрещено** — копия получила бы `string_view` на чужие строки.
- `run()` пишет в `m_times[i]` по индексу — индексы совпадают с порядком фаз.

## 4. Использование

```cpp
Phases::Schedule schedule;
schedule.add("commands", [&] { apply_commands(); })
        .add("spells",   [&] { run_spells(); })
        .add("terrain",  [&] { apply_edits(); });
schedule.insert_after("spells", "machines", [&] { step_machines(); });
schedule.run();
for (const auto& t : schedule.times()) std::println("{} {:.2f} ms", t.name, t.milliseconds);
```

В проекте расписание есть у `SpellSim::Simulation` (фазы тика симуляции); пример — `Modules/Phases/examples/01_schedule.cpp`.

## 5. Что менять осторожно

- **Нельзя менять расписание изнутри фазы** (вставлять/удалять во время `run()`): цикл идёт по индексам и ссылке на `Phase`, `insert` может перераспределить вектор — ссылка станет висячей. Если понадобится динамика, откладывай изменение до конца `run()`.
- Порядок фаз влияет на хеши симуляции: изменение порядка в `SpellSim` = обновление golden-эталонов.
- `std::function` — выделение памяти на каждую фазу при добавлении и косвенный вызов; на горячий путь (несколько десятков вызовов в тик) это не влияет.
- Уникальность имён проверяется только `FLUX_ASSERT` (в Release он тоже срабатывает — это не `assert`), так что ошибка видна сразу.

## 6. Упражнения для переписывания

1. Добавь зависимости между фазами (`after = {"spells"}`) и топологическую сортировку — как в `RuntimeSystem::Module::depends_on`.
2. Вынеси «отложенные изменения»: `schedule.defer([&]{ ... })`, применяемые после `run()`, и сделай изменение расписания из фазы безопасным.
3. Замени `std::function` на шаблонный параметр и измерь разницу — стоит ли?
4. Сделай `run_until(name)` для отладки «выполнить только первые N фаз» (шаг за шагом в оверлее).
