# RuntimeSystem — ядро игры без графики {#mainpage}

RuntimeSystem — то, что нужно и клиенту, и **выделенному серверу**: шина событий, планировщик задач, арены тика
и кадра, фиксированный шаг симуляции и **модули с жизненным циклом**. Здесь нет ни окна, ни GPU, ни GLFW —
модуль собирается и тестируется сам по себе (`cmake -S Modules/RuntimeSystem`).
Подключение: `#include <RuntimeSystem/RuntimeSystem.hpp>`, CMake-цель `engine::RuntimeSystem`.
Зависимости: MemorySystem, JobSystem, EventSystem.

## Слои

```
 клиент:   Core::App ─ окно, рендер, ввод ─┐
                                           ├─►  RuntimeSystem::Runtime ─ шина · задачи · память · тик · модули
 сервер:   main() ─ Runtime::run() ────────┘
```

Игровая логика пишется как RuntimeSystem::Module и не знает, где она запущена.

## Жизненный цикл модуля

| Фаза | Хук | Что делать |
|---|---|---|
| сборка | конструктор + `depends_on("Имя")` | объявить зависимости |
| `Runtime::initialize()` | `declare()` всех модулей | объявить события шины (`bus().declare_module(…).produces<…>()`) |
|  | `init()` по порядку зависимостей | создать ресурсы, взять писателей и читателей |
| кадр | `frame()` | ввод и интерполяция (идёт и на паузе) |
| тик | `tick()` по порядку | логика симуляции |
| `Runtime::shutdown()` / `~Runtime()` | `shutdown()` в обратном порядке | освободить ресурсы (не бросает) |

Порядок `init` — топологическая сортировка зависимостей; при равенстве — порядок `add()`. Зависимость
инициализируется раньше, а завершается позже зависимого: в `shutdown()` модуля его зависимости ещё живы.

## Гарантии

- `shutdown()` вызывается **только** у модулей с успешным `init()` и **ровно один раз**.
- `init()` бросил → уже поднятые модули завершаются в обратном порядке, фаза `Stopped`, исключение летит дальше.
- Исключение в `tick()` не пропадает; завершение модулей произойдёт в деструкторе (или раньше — вручную).
- Ошибки контракта (дубликат имени, неизвестная зависимость, цикл, вызов не в той фазе) — RuntimeSystem::RuntimeError
  с именами модулей в тексте; ошибка зависимостей бросается до первого хука.
- Тик: модули → `set_tick_callback` игры → `EventBus::advance_tick()` → смена арен тика. События и память тика N
  читаются в тике N+1.

## Сервер без окна

```cpp
RuntimeSystem::Runtime server({.ticks_per_second = 60.0});
server.add<Net>();
server.add<World>();
server.run({.realtime = true});          // темп по часам; request_stop() — выход
server.run({.max_ticks = 600, .realtime = false}); // прогнать вперёд без ожидания (тесты, симуляция)
```

## Стоимость (Release, бенчмарки модуля)

Тик пустого Runtime — около 7 нс (ручной цикл `advance_tick + swap` — 3 нс); каждый модуль в тике добавляет
около 2 нс. Замер времени модулей (`RuntimeConfig::profile_modules`) стоит около 60 нс на модуль и **выключен по умолчанию**.
Запуск 1000 модулей в худшем порядке зависимостей — около 4 мс (сортировка O(n²), один раз при старте).

## Что дальше (вне этого модуля)

Разбиение тика на фазы с автоматическим параллелизмом по объявленному чтению/записи, сетевой слой и ввод-команды
за тик (предсказание клиента) строятся поверх этого интерфейса.
