## 1. Что было в системе

| Что | Есть? |
|---|---|
| `ExternalLibrary/glad` | только загрузчик **OpenGL 4.5 core** (glad 0.1.36) — Vulkan в нём нет |
| Vulkan SDK (Arch-пакеты) | заголовки и загрузчик 1.4.357, слои валидации, `glslc`, `shaderc`, драйвер RADV (RX 7900 XTX) |

Решение: glad остаётся загрузчиком для OpenGL-бэкенда; Vulkan берётся из системы (`find_package(Vulkan)`),
GLSL → SPIR-V компилирует **shaderc во время работы** (`libshaderc_shared`; статическая `shaderc_combined` в Arch
без glslang и не линкуется — CMake ищет обе). Нет Vulkan или shaderc — модуль собирается только с OpenGL.

## 2. RHI — как устроено и почему так

```
 игра / Renderer2D / Renderer3D / Voxel           ← ни одного вызова API
          │  RHI::Device, ручки, DrawCall, PipelineDesc, один GLSL с макросами FLUX_*
 ┌────────┴─────────┐
 OpenGLDevice        VulkanDevice
 (glad, VAO-кэш,     (dynamic rendering, sync2, кольцо кадра, дескрипторы,
  кольцо UBO)         отложенное удаление, swapchain или без окна)
```

**Модель — машина состояний, как OpenGL**, а не графы рендера: `bind_target / clear / draw`. Поэтому
Renderer2D и Renderer3D переписались почти механически («не переписывать весь код»), а игры поменяли лишь
типы (`GL::Framebuffer` → `RenderTarget`, `GL::Mesh` → `Mesh`, `GL::Texture` → `Texture`).

Главные решения:

| Решение | Зачем |
|---|---|
| Ручки-числа + RAII-обёртки (`Texture`, `RenderTarget`, `Mesh`, `Pipeline`) | ручку можно хранить в ECS и событиях (ZII), владение — отдельно |
| Один GLSL, бэкенд добавляет `#version` и макросы (`FLUX_LOCATION`, `FLUX_VARYING`, `FLUX_UNIFORM(set, binding)`, `FLUX_SAMPLER`, `FLUX_POSITION`) | шейдер пишется один раз; GL 3.3 игнорирует set/binding (привязки выставляет бэкенд по именам `Frame`, `Draw`, `u_texture`) |
| Блоки uniform через `push_uniform` в память кадра + `DrawCall::draw_uniforms` | одинаково дешево на обоих API (GL — кольцо UBO, Vulkan — динамические смещения) |
| Ось Y и глубина как в OpenGL везде | Vulkan: отрицательная высота viewport + `FLUX_POSITION` переводит z; камеры и glm не трогали |
| `RenderTarget::uv()` | в GL строка 0 текстуры — низ, в Vulkan — верх: один вызов скрывает разницу |
| Vulkan: один кадр в полёте, кольцо кадра, «обновление буфера, уже нарисованного в этом кадре, создаёт новый» | проще всего правильный аналог orphaning'а; следующий шаг — 2–3 кадра в полёте и VMA |
| Ленивые проходы: очистка до рисования = `loadOp CLEAR`, посреди прохода — `vkCmdClearAttachments` | API Renderer2D/3D (`clear`, `begin`, `end`) не изменился |
| Vulkan без окна (без поверхности) | тесты и автопрогоны без показа; Core рисует «экран» в свою цель |

**Что нашли тесты и бенчмарки (и исправлено):**

| Находка | Кто нашёл |
|---|---|
| Цель с mip-уровнями: начало прохода переводило в нужную раскладку только уровень 0 | слои валидации Vulkan (CardDuel) |
| Вложение рендеринга смотрело на все mip-уровни (нужен ровно один) — отдельный view уровня 0 | то же |
| Stream-буфер > 8 МиБ не помещался в блок кольца кадра — блоки стали переменного размера | бенчмарк Renderer2D на 131 072 спрайтах; добавлен тест «кадр больше блока кольца» |
| Клики мыши между кадрами терялись (ещё конспект 7) | интеграционный тест Core |

## 3. Цифры

| Проверка | OpenGL | Vulkan |
|---|---|---|
| FallingSand, кадр 1280×720 | эталон | **0 отличающихся пикселей** |
| Voxel `--autopilot --ticks 600` | сумма `60ffe6924a65b951` | та же; кадр отличается в 116 пикселях из 921 600 (столбики профайлера) |
| CardDuel `--autoplay --fast --ticks 900` | `fccc1696468ab3ae` | та же |
| RuneCell `--autoplay --ticks 2400` | `b9c4e61d7334aa52` | та же |
| Renderer3D, 1024 лит-объекта, кадр с ожиданием GPU | 4.9 мс | **0.67 мс** |
| Renderer2D, 131 072 спрайта, 1080p | 5.4 мс | 5.8 мс |
| Слои валидации Vulkan во всех тестах и играх | — | 0 сообщений (тесты требуют ноль) |

Vulkan в Renderer3D быстрее: нет проверок состояния драйвера на каждый вызов, uniform — простая запись в кольцо.
В Renderer2D паритет — там узкое место в заливке вершин, а не в API.

## 4. Voxel на RHI

- `GpuMesh` (свой VAO/VBO) → `Mesh` с `VertexLayout` (позиция + RGBA8, 16 байт); `GL::Shader` → `Pipeline`
  со своим GLSL (туман) — один текст на оба API; `Frustum` и `Camera3D` — из модуля.
- Обзор мышью — в `Game::frame()`, рисование — в `Game::render_3d()`; захват курсора — `Window::set_cursor_mode`.
- stb не используется: шум — свой (`hash3` + value noise), как и просили.
- Пункты конспекта 6 «в модуль» (4.1 и 4.2.1) закрыты: в Voxel больше нет ни одного вызова графического API.

## 5. RuneCell — заклинание как живая клетка

| Биология / химия | Магия | Код |
|---|---|---|
| мембрана (мягкое кольцо: пружины, изгиб, давление) | форма и «оболочка» заклинания; Земля — жёсткость | `Cell`, `Physics::step_cell` — параллельно по клеткам |
| ядро | стихия клетки, выпускает ману | `Cell::nucleus` |
| атомы с валентностью | руны: Огонь 2, Вода 2, Земля 4, Воздух 1, Свет 3 | `Rune` (ECS) |
| ковалентные связи 1–3 | связи рун; расходуют валентность | `Bond` — сущность со ссылками `Entity` (поколения!) |
| молекула, насыщенность | устойчивая молекула поглощает ману | `Chemistry::classify` (union-find) |
| радикалы, реакции | свободная валентность мерцает и теряет энергию; соседние радикалы сами связываются | `Chemistry::react` |
| ароматика (бензол) | кольцо в молекуле — резонанс, +50% силы | цикл в union-find |
| метаболизм | частицы маны → устойчивые руны → поток энергии по связям | `Metabolism`: `Pool<Mote>` + `parallel_for` + `ChunkBuffers` |
| митоз | клетка делится надвое; разрезанные связи рвутся | `Chemistry::divide` по `cell.division_request` |

Заклинание: урон от Огня, лечение от Воды, скорость от Воздуха, усиление от Света и колец; формула как химическая
(`Ig₂Ve₂ · Te₆Ve₆◯`). Для неё в шрифт по умолчанию добавлены индексы (U+2070–209F), математика (≡, −) и геометрия (◯).

## 6. Теги памяти (набросок, как в Kohi)

`MemorySystem::MemoryTag` (Engine, Events, ECS, Jobs, Renderer, Game, Scratch, Untagged) — параметр `Arena::reserve`,
`Pool::reserve`, `DoubleArena::reserve`. Учитывается **подтверждённая** память (commit/decommit), пик и число арен,
счётчики атомарные. `MemorySystem::memory_report()` — таблица; Core печатает её по F1 и при выходе.
Уже размечено: память тика (Engine), кадра (Scratch), арены потоков JobSystem (Jobs), пулы Voxel и RuneCell (Game).

Настоящий отчёт RuneCell (`--autoplay --ticks 600`, конец работы):

```
tag           committed         peak  arenas
engine        128.0 KiB    128.0 KiB       2      ← память тика (две арены)
jobs                0 B          0 B      16      ← арены 16 потоков: RuneCell их не трогает (CardDuel — да)
game           64.0 KiB     64.0 KiB       1      ← пул частиц маны
scratch             0 B          0 B       1      ← память кадра
total         192.0 KiB
```

Уже по нему видно полезное: 16 арен потоков по 64 МиБ резерва не стоят ничего, пока не используются
(учитывается подтверждённая память, а не резерв).

## 7. Рекомендации по отладке

### 7.1. «Дерево событий» — делай его деревом причин, а не деревом типов

Иерархия типов событий (наследование `DamageEvent : CombatEvent`) ломает то, на чём стоит шина: тривиально
копируемые структуры, SoA-раскладку, ID по имени. Две полезные иерархии вместо неё:

1. **Иерархия имён** — уже есть: `duel.outcome`, `rune.bond_changed`. Инспектор строит дерево по точкам
   и фильтрует по префиксу (`rune.*`). Ничего не стоит в рантайме.
2. **Дерево причин (causality)** — вот что реально помогает отлаживать «почему это случилось»:
   - каждое событие получает порядковый номер `serial` и номер события-причины `cause`;
   - хранить это **рядом с данными в канале**, а не в пользовательской структуре: параллельные массивы
     `serial[] / cause[] / module[]` в EventBuffer — события остаются плоскими;
   - причину ставит система: `CauseScope scope(writer, input_event_serial)` на время обработки входного события;
   - журнал — кольцевой буфер в памяти (тег Events) на последние N тиков; в отладочной сборке (`FLUX_EVENT_TRACE`);
   - инспектор: выбрал событие → вверх по `cause` до `platform.key`, вниз — всё, что оно породило.
   На примере CardDuel: клик → `duel.command` → `duel.outcome` ×5 → `duel.fx` ×5 — одно дерево вместо пяти каналов.

### 7.2. Теги памяти — следующие шаги

- **Бюджеты**: `set_budget(MemoryTag::Events, MiB(32))` + проверка в `track_commit` (assert в отладке, лог в релизе).
- **Утечки**: при выходе у всех тегов `arenas == 0`; иначе печатать, какой тег не отпустил память.
- **Стандартные контейнеры**: `std::pmr`-ресурс с тегом (как ArenaResource, но с учётом в `memory_report`) —
  тогда в отчёт попадут `std::vector` ECS и шины.
- **Дельта за кадр** на оверлее F1: рост тега от кадра к кадру — первый признак утечки.

### 7.3. Остальное, что окупается

| Инструмент | Что даёт | Что уже есть |
|---|---|---|
| Детерминированный реплей | записать `platform.*` + seed → воспроизвести баг сколько угодно раз | детерминизм и контрольные суммы во всех играх |
| Контрольная сумма **каждого тика** | найти тик, где разошлись два прогона (desync) | сумма в конце; легко сделать потиковую |
| Слои валидации Vulkan + имена объектов (`VK_EXT_debug_utils`) | ошибки синхронизации и раскладок — с именем ресурса и прохода | валидация есть, имён пока нет |
| RenderDoc / `KHR_debug` метки проходов | видеть кадр по шагам | нет |
| Tracy (зоны профилировщика) | вместо самописных профайлеров в каждой игре | самописные профайлеры |
| ASan/UBSan, TSan для JobSystem | гонки и UB в параллельных системах | опции `*_SANITIZE` в модулях |
| Безоконный режим (Vulkan) | все GPU-тесты в CI без дисплея | есть |
