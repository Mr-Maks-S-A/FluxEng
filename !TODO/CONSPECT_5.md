## 2. JobSystem: устройство

Подключение: `#include <JobSystem/JobSystem.hpp>`, цель `engine::JobSystem`.
Зависит от MemorySystem (временные арены потоков) и `Threads::Threads`. Собирается отдельно:
`cmake -S Modules/JobSystem`.

### Три уровня API

| Уровень | Что | Когда |
|---|---|---|
| `Scheduler` + `JobCounter` | `run(counter, job)`, `wait(counter)` | разнородные задачи: загрузка, генерация |
| `TaskGroup` | счётчик + ожидание в деструкторе | «запусти три вещи и дождись» |
| `parallel_for` / `parallel_reduce` / `ChunkBuffers` | цикл по диапазону, нарезанный на куски | системы ECS: движение, поиск целей |

```cpp
JobSystem::Scheduler jobs;                 // фоновых потоков: ядра − 1
JobSystem::parallel_for(jobs, bodies.size(), 1024, [&](std::size_t begin, std::size_t end) {
    for (std::size_t i = begin; i < end; ++i) bodies[i].position += bodies[i].velocity * dt;
});
```

### Решения и почему

1. **`wait()` не спит, а помогает.** Пока счётчик не обнулился, ждущий поток сам берёт задачи
   из очереди. Отсюда: задача может запустить подзадачи и ждать их (вложенный `parallel_for`)
   без взаимной блокировки, а поток игры не простаивает.
2. **`threads = 0` — всё в вызывающем потоке.** Это не «особый режим», а тот же код:
   `parallel_for` просто идёт по кускам по порядку. Удобно для отладки и как эталон для сравнения.
3. **parallel_for не кладёт задачу на каждый кусок.** Запускается не больше `threads()` помощников,
   каждый забирает номер следующего куска одним `fetch_add`. Очередь трогается раз на помощника.
4. **Общая очередь под мьютексом, без work-stealing.** При «весомых» кусках (десятки мкс)
   очередь не узкое место; сложность work-stealing деков не окупается. Если когда-нибудь
   понадобятся тысячи мелких задач — это место для замены, API не изменится.
5. **Исключения не теряются.** Первое исключение задачи сохраняется в `JobCounter`, `wait()`
   его перебрасывает; остальные задачи доделываются.
6. **ZII:** `JobCounter{}` — «ничего не запущено», `wait()` на нём возвращается сразу.
   `ChunkBuffers{}` — ноль буферов.
7. **Временная память потока:** `jobs.scratch()` — своя `MemorySystem::Arena` у каждого потока
   (0 — вызывающий, 1…N — рабочие). Выделение без блокировок, освобождение — `ArenaScope`.
8. **Задача уничтожается до обнуления счётчика.** Иначе ждущий поток мог бы выйти из `wait()`
   и снять со стека то, на что ссылаются захваты лямбды, пока её деструктор ещё работает.

## 3. Детерминизм: главное правило

Многопоточность обычно ломает воспроизводимость: кто первым взял кусок, тот первым и записал.
JobSystem устроен так, что **результат не зависит от числа потоков**, если соблюдать три правила:

1. **Нарезка фиксирована.** Кусок `i` — это `[i·grain, min((i+1)·grain, count))`. Границы зависят
   только от `count` и `grain`, не от потоков.
2. **Кусок пишет только своё.** Свою строку массива, свой элемент, свой буфер. Общее — только читает.
3. **Собранное сливается по номеру куска, одним потоком.** `ChunkBuffers::for_each` идёт по кускам
   0, 1, 2…; `parallel_reduce` складывает частичные результаты в том же порядке.

```cpp
JobSystem::ChunkBuffers<ShotEvent> shots;
shots.reset(JobSystem::chunk_count(towers.size(), 32));
JobSystem::parallel_for(jobs, towers.size(), 32, [&](std::size_t begin, std::size_t end, std::size_t chunk) {
    for (std::size_t i = begin; i < end; ++i)
        if (auto shot = aim(towers[i])) shots[chunk].push_back(*shot);   // свой буфер куска
});
shots.for_each([&](const ShotEvent& s) { writer.emit(s); });             // один поток, порядок кусков
```

Даже сумма `float` (неассоциативная!) получается побитово одинаковой: порядок сложения фиксирован
(тест «parallel_reduce с float…», пример `02_parallel_for`).

**Как это связано с шиной событий.** Параллельная система не пишет в `EventWriter` из кусков —
она пишет в `ChunkBuffers`, а в шину отправляет главный поток после `parallel_for`. Шина остаётся
однопоточной, и порядок событий в канале — тот же, что при одном потоке.

**Как это связано с ECS.** Пока идёт параллельная система, структуру мира никто не меняет
(единственный владелец структуры работает первым в тике, отдельно). Поэтому `world.get<T>()`
const и `world.valid()` из кусков безопасны: это чистое чтение (проверено: в `World` нет
изменяемых кэшей, `component_id` — потокобезопасная статическая переменная).

## 4. Что нашли бенчмарки и как исправили

Бенчмарки писались не для красивых цифр, и первые же прогоны нашли две настоящие проблемы.

### 4.1. Системный вызов на каждую задачу

Первая версия: `run()` всегда делала `notify_one()`, `wait()` в цикле брала мьютекс, рабочие
сразу засыпали на условной переменной.

| Бенчмарк (3 потока) | Было | Стало |
|---|---|---|
| run + wait одной пустой задачи | 22.7 мкс | 4.3 мкс |
| пачка 1000 задач | 17.1 мс | 1.3 мс |
| пустой parallel_for | 68 мкс | 22 мкс |

Исправление:
- `m_queued` (атомарный счётчик очереди) — `try_pop` смотрит в него и не берёт мьютекс,
  если очередь пуста;
- `m_sleeping` — будим (`notify_one`) только если кто-то спит. Гонки «пропущенного пробуждения»
  нет: засыпающий увеличивает `m_sleeping` под мьютексом и перепроверяет очередь, а `run()`
  кладёт задачу под тем же мьютексом и смотрит `m_sleeping` после. Тест «уснувший рабочий поток
  просыпается…» строит ситуацию, в которой потерянное пробуждение = зависание;
- рабочий поток перед сном ~десятки мкс крутится с инструкцией `pause`: задачи следующей
  системы того же тика подхватываются без системного вызова.

Оставшиеся ~1.3 мкс на задачу в пачке — цена общей очереди под мьютексом. Для систем это
неважно (parallel_for раздаёт куски атомарным счётчиком, а не очередью), но **мелкие задачи
по одной** — плохая идея; см. «Что дальше».

### 4.2. False sharing в ChunkBuffers

Буферы кусков лежали в `std::vector<std::vector<T>>` подряд: заголовки соседних векторов
(begin/end/capacity, 24 байта) делили одну кэш-линию, и потоки, пишущие в соседние куски,
дрались за неё. Сбор событий ускорялся всего в ×1.2 на 4 ядрах.
Исправление — каждый буфер в своей линии (`struct alignas(64) Slot`): ×2.7.

| BM_Events (1M элементов) | 0 потоков | 1 | 2 | 3 |
|---|---|---|---|---|
| до | 10.3 мс | 7.4 | 7.7 | 7.0 |
| после | 10.1 мс | 5.5 | 4.2 | 3.3 |

### 4.3. Остальные цифры (после исправлений)

| Бенчмарк | 0 | 1 | 2 | 3 потока |
|---|---|---|---|---|
| Integrate 1M (лёгкая работа, упирается в память) | 0.94 мс | 0.54 | 0.46 | 0.32 |
| Neighbours 100k (тяжёлая, 64 соседа на элемент) | 70.1 мс | 32.4 | 21.5 | 16.8 |

`BM_Grain` показывает, зачем нужен «весомый» кусок: при grain = 64 тот же цикл в 15 раз
медленнее, чем при grain ≥ 4096. Правило: кусок — десятки микросекунд работы.

### 4.4. Ошибка в моём же тесте

Тест «у каждого потока своя арена» предполагал, что 3 задачи выполнят 3 рабочих потока.
Но `wait()` помогает — и одну задачу брал ждущий поток (индекс 0). Тест переписан: 4 задачи
одновременно (3 рабочих + ждущий), проверяется «разные потоки → разные арены, индексы 0…3».
Это хорошая иллюстрация пункта 1 из раздела 2: ждущий поток — полноценный исполнитель.

## 5. Core и Swarm на JobSystem

**Core.** `App` владеет `JobSystem::Scheduler` (`app.jobs()`), число фоновых потоков —
`AppConfig::threads` или `--threads N` (по умолчанию ядра − 1, 0 — главный поток). При старте
печатается `job threads: N background + main`. Игра уничтожается раньше `App`, поэтому
планировщик переживает всё, что игра в него положила.

**Swarm.** Steering (90% тика) читает снимок сетки и пишет только скорость своего агента —
идеальный кандидат. Movement — тоже построчно.

| 200 000 агентов | 0 потоков | 1 | 3 |
|---|---|---|---|
| steering | 55.0 мс | 35.2 | 18.6 |
| весь тик | 62.1 мс | 42.0 | 25.4 |
| контрольная сумма | `aedddd17…` | `aedddd17…` | `aedddd17…` |

**T** в игре переключает системы между `app.jobs()` и собственным `Scheduler{threads = 0}`
игры — тот же код, другой планировщик; можно сравнить вживую по столбикам.

Закон Амдала в действии: теперь 30% тика — последовательная сортировка сетки (6.8 мс
из 25 при 200k). Дальше ускорять надо её, а не Steering.

## 6. Siege

Оборона замка: волны врагов от трёх ворот слева, замок справа, три стены с проходами.
Строитель (ИИ) ставит башни — лучников и мортиры (урон по площади); башни перекрывают
проходы, враги перестраивают маршрут, и получается лабиринт. Игрок может помогать мышью.

### 6.1. Модули и события

```
Platform ──key/mouse──► Economy, Settings
Waves ──siege.spawn──► Lifecycle
Navigation ──siege.breach──► Lifecycle, Economy           (∥, ChunkBuffers)
Targeting ──siege.shot (SoA)──► Ballistics                (∥, ChunkBuffers)
Ballistics ──siege.impact (SoA)──► Damage                 (∥, ChunkBuffers, мортира — по площади)
Damage ──siege.killed (SoA)──► Lifecycle, Economy
Economy ──siege.build──► Lifecycle, Navigation            (оценка клеток — parallel_reduce)
```

Порядок тика: **Lifecycle** (единственный владелец структуры: уничтожает убитых и прорвавшихся,
рождает врагов, ставит башни) → Waves → **Grid** (∥, память тика) → **Navigation** ∥ →
**Targeting** ∥ → **Ballistics** ∥ → Damage → **Economy** (∥ оценка).

Цикл в графе (Navigation → breach → Economy → build → Navigation) — законная обратная связь:
шина N → N+1 его разрывает, отчёт шины показывает его как `[cycle]`.

### 6.2. Что каждый модуль движка здесь делает

| Модуль | Где |
|---|---|
| ECSSystem | враги: `Body` (16 байт, плотно), `Health`, `Stats`; башни: `Tower`. Ссылки в событиях — `Entity` с поколением: выстрел по уже уничтоженному врагу отсеивается (`wasted hits`) |
| EventSystem | 6 своих каналов; массовые — SoA: до 570 000 `siege.impact` за прогон, колонки читаются как `std::span` |
| MemorySystem | сетка врагов (позиции, здоровье, «шагов до замка») строится каждый тик в арене тика; ни одного malloc |
| JobSystem | Grid, Navigation, Targeting, Ballistics — `parallel_for` + `ChunkBuffers`; строитель — `parallel_reduce` с top-K кандидатов |
| Core / Window / Renderer | окно, ввод → события, фиксированный тик, профайлер-оверлей (параллельные системы — в рамке) |

### 6.3. Интересные места

- **Поле потоков** (BFS от замка + направление «вниз по склону» для каждого тайла) — чистые данные.
  Navigation и Economy держат **свои копии** карты и обновляют их по `siege.build`: модулю не нужен
  доступ к чужим данным. Economy проверяет на своей копии, что новая башня не перекроет путь.
- **Строитель полностью детерминирован при параллельной оценке.** Каждый кусок строк карты
  возвращает своих 6 лучших кандидатов, слияние — в порядке кусков, порядок кандидатов строгий
  (очки, при равенстве — номер тайла). Убывающая отдача (вес тайла маршрута делится пополам
  за каждую башню, уже до него достающую) разносит башни вдоль всех трёх маршрутов, а не в кучу.
- **Убитый враг живёт ещё тик.** Damage ставит `hp ≤ 0` и шлёт `siege.killed`; уничтожит его
  Lifecycle в начале следующего тика. Все системы смотрят на `hp` в снимке сетки и пропускают
  таких — поэтому «мёртвые» не идут к замку и не притягивают выстрелы.

### 6.4. Цифры

Обычная игра с волны 0: до волны 12 (3 минуты) строитель держит замок (~300 башен), тик < 3 мс.
Волны растут в 1.4 раза, здоровье — в 1.12, доход — медленнее; замок рано или поздно падает,
и игра продолжается в «бесконечном» режиме.

Нагрузка: `--wave 18 --cap 100000 --ticks 900 --no-draw`:

| система | 0 потоков | 3 потока |
|---|---|---|
| grid ∥ | 2.83 мс | 1.24 |
| navigation ∥ | 6.85 мс | 2.29 |
| targeting ∥ | 0.14 мс | 0.10 |
| ballistics ∥ | 0.03 мс | 0.03 |
| economy ∥ | 1.90 мс | 1.04 |
| остальное | 0.15 мс | 0.15 |
| **тик** | **11.9 мс** | **4.8 мс** |

82 233 врага в пике, 601 башня, 572 190 попаданий, 50 119 убийств — и одна и та же контрольная
сумма `9b19df8e42228774` при 0 и 3 потоках.

бите. Гарантия JobSystem — одинаковый результат **при любом числе потоков на одной сборке**.

```sh

cmake -S Modules/JobSystem -B /tmp/job-tsan -DJOBSYSTEM_SANITIZE=thread && cmake --build /tmp/job-tsan && ctest --test-dir /tmp/job-tsan
build/bin/Siege --ticks 3000 --no-draw --threads 0   # сравнить последнюю строку с прогоном без --threads
```

## 8. Что дальше

1. **Параллельная сортировка сетки** (Swarm, Siege): гистограммы по кускам → префиксная сумма →
   раскладка по кускам. Это сейчас главный последовательный участок тика.
2. **Граф систем вместо ручного порядка.** Контракты модулей уже знают, кто что читает и пишет
   (события). Если добавить к контракту компоненты ECS (`reads<Body>()`, `writes<Health>()`),
   можно автоматически запускать независимые системы одновременно (например, Targeting и
   поиск пути строителя), а конфликты ловить на этапе `build_graph()`.
3. **Work-stealing очередь** — только если появятся тысячи мелких задач за тик
   (сейчас 1.3 мкс на задачу через общую очередь).
4. **Время простоя потоков в профайлере**: `SchedulerStats` уже считает задачи; стоит добавить
   время простоя рабочих потоков — тогда видно, хватает ли им работы.
5. **Текст в рендере** (из конспекта 4) — в Siege особенно не хватает чисел на экране:
   золото, волна, целостность сейчас в заголовке окна и полосках.
