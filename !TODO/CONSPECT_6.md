## 1. Коротко

`Sandbox/voxel/main.cpp`, 1150 строк. Бесконечный мир из чанков 16×16×96 (рельеф, пещеры, деревья),
ходьба с прыжком и столкновениями, полёт, ломать/ставить 8 видов блоков, осколки, затенение углов (AO),
туман, отсечение по пирамиде видимости, подгрузка и выгрузка чанков вокруг игрока.

Единственная правка движка — `Core::AppConfig::pause_key` (Space в 3D — прыжок, а не пауза; в Voxel пауза на P).

**Главный вывод:** логика (данные, события, потоки, память) легла на существующие модули без
изменений. Не хватает всего, что касается **3D-вывода и ввода**: примерно 40% кода игры —
рендер, камера, ввод мыши, математика — это будущий код модулей.

| Часть файла | Строк | Чья это работа |
|---|---|---|
| блоки, чанки, шум, генерация | ~120 | игра (но шум — в общую математику) |
| Terrain: владелец блоков, подгрузка | ~110 | игра / будущий VoxelWorld |
| Mesher: сетки с AO | ~175 | будущий VoxelWorld (мешинг) |
| луч DDA, столкновения AABB | ~115 | **модуль: физика вокселей / math** |
| свой 3D-рендер (GpuMesh, Frustum, шейдер) | ~190 | **модуль: RendererSystem 3D** |
| игра: камера, мышь, оверлей, сводка | ~185 | частично **Core / WindowSystem** |
| события, компоненты, Interaction, Debris, профайлер | ~195 | игра |

## 2. Как устроена игра

Тик 60 Гц (Core), модули-структуры как в других играх:

```
Controller   ── ходьба/полёт, AABB-столкновения с блоками           (читает platform.key)
Interaction  ── луч из глаз: ЛКМ/ПКМ → voxel.block_edit              (читает platform.mouse_button, key)
Terrain      ── ЕДИНСТВЕННЫЙ владелец блоков:
                 правки прошлого тика → voxel.block_changed
                 ∥ генерация недостающих чанков → voxel.chunk_loaded
                 выгрузка дальних → voxel.chunk_unloaded
Mesher       ── по событиям помечает «грязные» чанки, ∥ строит сетки (кусок = чанк)
Debris       ── осколки сломанных блоков (сущности ECS)
render()     ── обзор мышью, загрузка новых сеток на GPU, 3D-отрисовка; потом 2D-оверлей Core
```

Решения, которые стоит сохранить:

- **Чанк в `Pool<ChunkBlocks>`**: 24 КиБ, обнулённый чанк — воздух (ZII). Выгрузка — `pool.free()`,
  блок обнуляется и готов к следующему чанку, никаких `new`/`delete`.
- **Генерация пишет только свой чанк** (деревья не выходят за край) — поэтому чанки генерируются
  параллельно без синхронизации. В настоящем движке деревья через границу делаются вторым проходом
  («декорации» после того, как готовы соседи).
- **Сетка помнит, какие соседи были при постройке** (4 бита). Новый чанк перестраивает соседа,
  только если тот строился без него. Без этого стартовый мир строился дважды (394 сетки на 197 чанков).
- **Рендер узнаёт о новой сетке по номеру версии**, а не по событию: GPU живёт в домене кадра,
  сетки — в домене тика. Это та же граница «тик/кадр», что и в конспекте 4, теперь для GPU-ресурсов.
- **Состояние клавиш собирается из событий** `platform.key` (`held[]`), а не читается из окна в тике —
  движение детерминировано и воспроизводимо.

## 3. Что из модулей подошло как есть

| Модуль | Как использован | Замечания |
|---|---|---|
| MemorySystem | `Pool<ChunkBlocks>` — тысячи чанков без аллокаций | идеально подошёл; ZII = «воздух» |
| JobSystem | генерация и мешинг: `parallel_for`, кусок = чанк | стартовый мир ×3.4 быстрее на 4 ядрах; одинаковая сумма при любом `--threads` |
| EventSystem | правки блоков, загрузка/выгрузка чанков | граница «кто владеет блоками» прошла по событиям естественно |
| ECSSystem | игрок, осколки | работает, но для одного игрока ECS избыточен (см. ниже) |
| RendererSystem | `GL::Shader` + 2D-оверлей (прицел, панель блоков, профайлер) | `Shader` удобен; остальное — 2D |
| Core | окно, тик, ввод → события, `app.jobs()`, `tick_alpha()` для плавной камеры | 2D-камера и WASD/колесо Core «работают вхолостую» |

## 4. Что пришлось написать в игре — кандидаты в модули

Отсортировано по важности для любой 3D-игры. В коде места помечены `[в модуль]`.

### 4.1. RendererSystem: 3D (главное)

1. **`Mesh` / `GpuBuffer`** — VAO + VBO с описанием раскладки вершины (`VertexLayout`), `upload()`,
   `draw()`, освобождение в деструкторе (RAII; в игре — ручной `release()`). Сейчас это `GpuMesh`.
2. **`Camera3D`** — позиция, yaw/pitch (или кватернион), FOV, near/far, `view()`, `projection()`,
   `view_projection()`, `forward()`. Сейчас собирается вручную из `glm::perspective` + `lookAt`.
3. **`Renderer3D` / проход рендера** — включение глубины и отсечения граней, очистка буфера глубины,
   порядок «3D, потом 2D-оверлей». Сейчас игра сама включает/выключает GL-состояния и полагается на то,
   что `Renderer2D::end()` выключит глубину. Нужен явный объект состояния (`RenderState`/`Pipeline`).
4. **Отсечение по пирамиде видимости** (`Frustum` из VP-матрицы + тест AABB) — отсекает ~65% чанков.
5. **Стандартные шейдеры**: «цвет вершины + туман», позже — текстурный атлас блоков, освещение.
6. **Очистка цветом и глубиной в одном вызове**: `Renderer2D::clear()` чистит только цвет.

### 4.2. WindowSystem: ввод для 3D

1. **Захват курсора**: `Window::set_cursor_mode(Normal / Hidden / Captured)`. Сейчас — прямой вызов GLFW
   через `native_handle()`.
2. **Относительное движение мыши** как полноценный ввод: `cursor_delta()` есть, но в шину событий оно
   не попадает, поэтому обзор живёт в домене кадра в обход событий. Нужно либо событие
   `platform.mouse_move` (суммарное смещение за тик), либо явное правило «обзор — кадровый ввод».
3. **Raw mouse motion** (`GLFW_RAW_MOUSE_MOTION`) для обзора без ускорения ОС.

### 4.3. Core: игры бывают не только 2D

1. **Встроенные клавиши как настройка, а не жёсткий код.** Сделано для паузы (`pause_key`);
   WASD/стрелки/колесо всё ещё двигают 2D-камеру — в 3D они должны отключаться
   (`AppConfig::camera_controls = false` или «профиль управления»).
2. **`Game::world_size()` и 2D-камера обязательны** — для 3D бессмысленны. Нужен вариант `Game`
   без 2D-мира или камера как часть игры, а не App.
3. **Кадровая и тиковая части игры** (тик — логика, кадр — обзор, загрузка GPU) — вынести в API:
   `Game::frame(App&, float dt)` до отрисовки, чтобы не делать ввод внутри `render()`.
4. **Синхронная обработка событий в `setup()`**: события стартовой загрузки видны только в первом
   тике. Игре пришлось строить сетки вручную в `setup()`. Варианты: «тик 0» до цикла или
   `bus.flush_setup()`.

### 4.4. Математика и физика (новый маленький модуль `Math` или часть Core)

1. **Шум**: value/Perlin/Simplex 2D/3D, fBm — сейчас ~80 строк в игре; нужен любой процедурной генерации.
2. **Луч по сетке (DDA)** — выбор блока, видимость, пули в воксельном мире.
3. **AABB и столкновения с сеткой** — «двигай по осям, упрись в блок»; то же пригодится в 2D (Colony, FallingSand).
4. **Детерминированный хеш** (`hash3`) — в каждой игре свой; один общий.

### 4.5. Кандидат в отдельный модуль: `VoxelWorld`

Если воксельный мир — цель движка (а к этому ведёт SoA-пример `02_soa_voxels` в EventSystem), то
Terrain + Mesher + raycast — это ядро будущего модуля:

- хранилище чанков с ключом `(cx, cz)`, `block_at()`, правки через события;
- подгрузка/выгрузка по радиусу с бюджетом на тик;
- мешинг (сейчас «грань на блок» + AO: 1.47 млн вершин на радиус 8). Следующие шаги — **greedy meshing**
  (в 4–8 раз меньше вершин) и **индексированные квады** (4 вершины вместо 6);
- освещение (небо + факелы) — заливка по сетке, тоже параллельно по чанкам;
- сохранение изменённых чанков (сейчас выгрузка забывает правки игрока!).

### 4.6. ECS: замечания

- Для одного игрока `world.get<Transform>(player)` в каждом месте — многословно. Нужен «синглтон-компонент»
  или ресурс мира (`world.resource<PlayerState>()`).
- Осколки — хороший случай для ECS (сотни коротко живущих сущностей), игрок — нет.

## 5. Предлагаемый порядок работ

| # | Что | Почему первым |
|---|---|---|
| 1 | WindowSystem: `set_cursor_mode`, raw motion | 20 строк, без этого любая 3D-игра лезет в GLFW |
| 2 | RendererSystem: `Mesh` + `VertexLayout`, `Camera3D`, `clear(color, depth)` | основа любого 3D; вынести `GpuMesh` почти как есть |
| 3 | Core: отключаемые 2D-управления, `Game::frame()`, `Game` без `world_size` | убрать «костыли» 3D-игры |
| 4 | Math: шум, DDA, AABB-столкновения, хеш | общий код для всех игр Sandbox |
| 5 | RendererSystem: `Frustum`, состояние конвейера, текстурный атлас блоков | качество и скорость 3D |
| 6 | VoxelWorld: чанки, мешинг (greedy), освещение, сохранение | если воксели — направление движка |

## 6. Цифры и проверки

4 ядра, Release. Отрисовка — программный OpenGL контейнера (llvmpipe), поэтому «render 3d» ~27 мс на кадр
отражает CPU-растеризацию, а не видеокарту.

| Замер | 0 фоновых потоков | 3 фоновых потока |
|---|---|---|
| стартовый мир, радиус 8 (197 чанков): генерация | 141.5 мс | 41.6 мс (×3.4) |
| то же: сетки (1.47 млн вершин) | 248.9 мс | 62.1 мс (×4.0) |
| подгрузка в полёте: terrain / тик | 0.46 мс | 0.20 мс |
| подгрузка в полёте: mesher / тик | 1.54 мс | 0.59 мс |
| контрольная сумма (`--autopilot --ticks 1800`) | `186606e8f602eb2f` | `186606e8f602eb2f` |

Автопилот за 1800 тиков: 966 чанков сгенерировано, 719 выгружено, 2271 сетка построена,
300 блоков сломано, 2400 осколков. Память: 247 чанков × 24 КиБ = 5.8 МиБ, вершины на GPU — 31 МиБ
(вот почему greedy meshing — первый пункт для VoxelWorld). Отсечение: рисуется ~85 чанков из ~250.

| Проверка | Результат |
|---|---|
| Все тесты движка (xvfb), включая smoke-тест `Sandbox.Voxel` | 257 / 257 |
| `--threads 0` и `3`, 1800 тиков автопилота | одна контрольная сумма |
| Windows (zig + wine), 300 тиков | та же сумма, что на Linux |

Как запускать:

```sh
build/bin/Voxel                                              # играть
build/bin/Voxel --autopilot --ticks 1800 --threads 0         # замер подгрузки; сравнить с запуском без --threads
build/bin/Voxel --radius 16                                  # дальность 16 чанков (~800 чанков)
```
