# Конспект 12 — журнал событий с избыточностью, зонтичные цели, идеи по улучшению

## 1. Модуль `EventLog`

Дописываемый журнал событий, который переживает повреждение носителя и обрыв записи. Подробно — `Modules/EventLog/README.md`.

- **Два слоя защиты.** Записи (`sync | длина | номер | тик | тип | данные | CRC-32C`) режутся на блоки и складываются в **полосы**:
  `k` блоков данных + `m` блоков чётности. Чётность — код Рида—Соломона над GF(2⁸) (матрица Коши): любые `m` испорченных блоков
  полосы восстанавливаются **полностью** (это RAID-5 при m = 1 и RAID-6 при m = 2, но для любых m). У блока свой CRC, номер полосы и номер
  блока — повреждение и «блок не на своём месте» видны.
- **Если восстановить нельзя** (стёрто больше m): уцелевшие блоки данных всё равно читаются, читатель перепрыгивает дыру по маркеру
  и CRC, а потерянные номера записей названы точно (`Gap`). **Недостоверную запись читатель не отдаёт никогда.**
- **Заголовок** в двух копиях; **обрыв записи** — недописанные блоки считаются стёртыми; `repair` переписывает исправленное, `resume`
  чинит и продолжает нумерацию после перезапуска.
- **Типизированные события:** `append(tick, Hit{…})` / `decode<Hit>(record)`; тип — FNV-1a 32 бита от `event_name`, тип и размер проверяются.
- **Хранилище — интерфейс** (`Storage`): `MemoryStorage` (в тестах можно портить байты) и `FileStorage` (с `fsync`).
- **Шина:** `BusAdapter.hpp` (цель `engine::EventLogBus`): `record(writer, tick, reader)` и `Replayer` — события шины ↔ журнал.
- `ErasureCode` годится отдельно для любых данных; `Math::crc32c` добавлен в `Math`.

Проверено: исчерпывающий перебор всех стираний ≤ m (k=5, m=3), 60 случайных прогонов «≤ m блоков в каждой полосе — не теряется ни одной
записи», 60 прогонов произвольного разрушения («читатель не падает и не возвращает ни одной недостоверной записи»), файл на диске,
обрыв записи, обе копии заголовка. 25 тестов, чистые под ASan + UBSan. Скорость: кодирование ≈ 1,2 ГБ/с, запись ≈ 3,5 млн событий/с,
чтение с восстановлением ≈ 3,9 млн событий/с.

Честные границы: код исправляет **известные** стирания — их находят CRC блоков; если CRC совпадёт случайно (вероятность 2⁻³²) на
испорченном блоке, он будет принят. Это защита от сбоев носителя и обрывов, а не от злонамеренной подмены (для неё нужна подпись/MAC).
Полоса целиком теряется, если стёрто больше m блоков одновременно — выбирайте m под носитель.

## 2. Зонтичные цели (`Modules/CMakeLists.txt`)

Одна библиотека на всё — плохая идея: пропадут самостоятельная сборка и тесты каждого модуля (`tools/check_modules.sh`), зависимости
станут невидимыми, а сборка — дольше. Вместо этого — **зонтичные INTERFACE-цели**: игре достаточно одной строки, модули остаются отдельными.

| Цель | Состав | Зачем |
|---|---|---|
| `engine::Foundation` | Math, MemorySystem, JobSystem, Phases | числа, память, потоки, расписание тика |
| `engine::Simulation` | Foundation + EventSystem, ECSSystem, Replay, EventLog | детерминированное ядро |
| `engine::Platform` | WindowSystem, RendererSystem, Core | окно, графика, каркас приложения |
| `engine::Gameplay` | Simulation + Terrain, ManaField, Runes, Character, SpellSim | правила мира заклинаний |
| `engine::Presentation` | Platform + WorldRender + адаптеры | отрисовка мира |
| `engine::FluxEng` | Gameplay + Presentation | всё сразу |

FirstSpell теперь линкуется одной строкой `engine::FluxEng`. Серверу без графики хватит `engine::Gameplay`, инструменту — `engine::Simulation`.

## 3. Как делить модули дальше (рекомендации)

**Держать отдельно** (и дальше): всё, что можно тестировать и собирать само по себе и у чего свой смысл (Terrain, ManaField, Runes, Character,
Replay, EventLog…). Граница модуля — это граница ответственности и зависимостей, а не размера файла.

**Что стоит сдвинуть:**
1. `Core::ActionMap` → `WindowSystem`. Он зависит только от `InputState` и кодов GLFW — это абстракция ввода, а не каркас приложения.
   `Core` оставит `App` и реэкспортирует. Тогда игра без `Core` (инструмент, тест) тоже получает действия.
2. `Math` — разделить, когда появится вторая «единица» или вторая форма: `SdfField`/`raycast`/`PlaneSdf`/`SphereSdf` → `Geometry`
   (туда же формы правок: коробка, капсула, CSG — нужны и ландшафту, и машинам), `Mana` → слой `Gameplay` (единицы игры).
   Пока форм мало — не делить: лишний модуль дороже, чем пять заголовков.
3. `Phases` — крошечный модуль; когда добавятся зависимости фаз и параллельный запуск, он сольётся по смыслу с `JobSystem` (`Foundation`).
   Пока удобно держать отдельным: чистая, проверяемая абстракция.
4. Пара `Replay` + `EventLog` — две части одной темы «сохранение прогона». Можно объединить в `Persistence`, но зависимости разные
   (Replay знает команды и хеши, EventLog — байты и события): лучше связать **вызовом** — запись повтора кладётся в журнал.
5. Именование: старые модули — `XSystem` (Memory, Job, Event, ECS, Window, Renderer), новые — просто имена. Выберите один стиль
   до публикации (я бы убрал суффикс: `Memory`, `Jobs`, `Events`, `Ecs`, `Window`, `Renderer`).
6. Единый заголовок `<FluxEng/FluxEng.hpp>` для зонтичной цели — по желанию; полезен для скриптов и примеров, вреден для времени сборки.

## 4. Идеи по улучшению модулей (по ценности)

**Надёжность и детерминизм**
1. **Эталонные записи в репозитории.** Положить короткий `.rec` и проверять, что любой компилятор/сборка даёт те же хеши
   (gcc и clang, Release и Debug). Один тест ловит всю «недетерминированность по платформам», пока она не вросла в код. Самое ценное.
2. **Именованные хеши подсистем** вместо трёх чисел: при расхождении (сеть, повтор) сразу видно, какая подсистема разошлась;
   `Replay::diff` покажет первый тик расхождения по каждой.
3. **Защитить записи повторов кодом EventLog** (сейчас `.rec` — обычный файл: один испорченный бит убьёт воспроизведение бага).
4. **Мир как «сид + журнал правок»**: сохранение — это `EventLog` с `TerrainEdited` и командами, загрузка — повтор с контрольными снимками
   изменённых чанков. Вместо 25 МБ — килобайты; совпадает с принципом ТЗ «мир пересоздаётся из сида и записи команд».

**Производительность**
5. **Первый кадр дороже бюджета (≈ 28 мс):** стартовая сборка 256 сеток блокирует кадр. Строить в фоне, показывать мир по мере готовности
   (ближние чанки первыми — очередь уже умеет).
6. **Перестройка меша только затронутых ячеек** и сглаживание нагрузки: `budget` по времени, а не по числу чанков.
7. `Phases` с декларацией читаемого/записываемого: независимые фазы запускать параллельно через JobSystem, а порядок проверять автоматически.

**Геймплей и язык**
8. **Руны: переменные и функции** — следующий этап языка. Это снимет ограничение «значение не живёт между операторами» (счётчики,
   `tunnel.rune` развернётся в граф) и откроет редактор на `Graph`: живая проверка по кодам `Diagnostic`, подсветка узла.
9. **Данные вместо констант:** стоимость рун, радиусы, диффузия, скорость — в файле настроек, перечитываемом по клавише
   (как заклинания). Балансировать без перекомпиляции.
10. **Мана через материалы:** проводимость породы и воздуха (вопрос из ТЗ), ветер/потоки (перенос), источники и стоки у жил.
11. **Формы правок (`SdfShape`)**: сфера, коробка, капсула, CSG — один интерфейс для заклинаний, инструментов и машин.
12. **Тела и машины:** обобщить `Character` до `Body` (капсула, жёсткое тело на сетке) с коллизией «поле против поля».

**Инструменты и документация**
13. Утилита `fluxctl`: просмотр/сравнение записей и журналов (`ReplayTool` уже есть), проверка и форматирование заклинаний, дамп журнала.
14. Doxygen для новых модулей (у старых есть); автоматическая проверка `tools/check_module_docs.sh` уже требует `@file` и примеры.
15. Фаззинг парсеров (`parse_program`, `parse_graph`, `Recording::load`) и читателя журнала — они принимают данные извне.
