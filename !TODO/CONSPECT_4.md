## 2. Core: память тика и кадра

```cpp
app.tick_arena();            // память текущего тика (DoubleArena::current)
app.previous_tick_arena();   // память прошлого тика: только чтение
app.frame_arena();           // временная память кадра: reset в начале каждого кадра
```

После каждого `bus.advance_tick()` Core вызывает `swap()`: всё, что выделено в тике N,
читается в тике N+1 и освобождается (обнуляется) после него — **та же модель, что у событий шины**.

Ещё два добавления:
- `Game::shutdown(App&)` — итоги после последнего кадра. Ecosystem печатает сводку популяций,
  Colony — склад, Swarm — таблицу производительности;
- `AppConfig::extra_args` — всё, что Core не разобрал, достаётся игре (`--agents 200000`, `--no-draw`).

## 3. Общая схема игр

Все четыре игры теперь устроены одинаково:

```
class Game : Core::Game {
    ECS::World world;          // общие данные — компоненты
    ModuleA a;  ModuleB b; …   // модули-структуры: порты + свои данные + declare() + tick()
    tick():   a.tick(world, …); b.tick(world, a, …);   // зависимости видны в сигнатурах
    render(): выборки const-компонентов
    shutdown(): сводка
};
```

**Правило одного владельца структуры.** Создавать и уничтожать сущности может только один модуль:

| Игра | Владелец | Остальные |
|---|---|---|
| FallingSand | Effects (вспышки) | — |
| Colony | World (ресурсы), Colonists (колонисты) | Jobs владеет компонентами брони `Reserved`, `AwaitingJob` |
| Ecosystem | Life | Rabbits, Foxes меняют только значения компонентов |
| Swarm | Population | Grid, Steering, Movement, Hazards только читают или меняют значения |

Это делает обход выборок безопасным: пока модуль идёт по `view`, никто не уничтожает сущности
под ним. Уничтожение идёт через событие — к владельцу, в следующем тике.

## 4. FallingSand

| Что | Как было | Как стало |
|---|---|---|
| структура | один класс, 8 полей портов, методы `tick_*` | модули Brush, Weather, Simulation, View, Effects |
| сетка | `std::vector` × 6 | `std::span` в арене уровня; `Material::Empty = 0` — нулевая память = пустой мир |
| список изменений тика | `std::vector` | `app.tick_arena()` + `ArenaScope`: выделение — сдвиг, освобождение — откат |
| `live_cells` | проход по 27 280 клеткам каждый тик | считается по ходу в `set_cell` |
| Weather | цепочка `if` по номеру тика | таблица источников `{x, y, material, period, phase}` |
| вспышки | `vector<Flash>`, анимации по одной | сущности `Flash + AnimationState`; все анимации — **один** вызов по плотному пулу |

**Проверка:** `--ticks 375` даёт **побайтно ту же** статистику шины, что до переписывания
(`sand.cell_changed` 295 570, `sand.ignited` 797). Логика симуляции не изменилась.

## 5. Colony

Колонисты и ресурсы — сущности, ресурсы в событиях — `Entity` с поколением.

**Что ушло благодаря поколениям:**

| Было | Стало |
|---|---|
| индексы ресурсов «никогда не переиспользуются», иначе запоздалое событие попадёт в новый ресурс | слоты переиспользуются: 48 слотов на все сущности за 4000 тиков |
| Jobs и Colonists обрабатывали `resource_depleted`, чтобы снять бронь и остановить колонистов | ресурс уничтожается; бронь (`Reserved`) исчезает вместе с ним; колонист проверяет `world.valid(target)` |
| `m_reserved_by`, `m_awaiting_job`, 8 параллельных `vector` в классе игры | компоненты `Reserved`, `AwaitingJob`, `Worker`, `Position`, `Anim`, временный `Carrying` |
| линейный поиск «занят ли тайл» по всем ресурсам | `tile_owner` в арене уровня: `Entity{}` — свободно, O(1) |

**Найденная ошибка.** В старой версии, если задание приходило на ресурс, который успел исчезнуть,
колонист оставался «в ожидании задания» навсегда: флаг снимался, только когда колонист начинал
работу. Теперь `AwaitingJob` хранит тик отправки, и через 2 тика Jobs назначает новое задание.

Граф событий упростился: `resource_depleted` теперь нужен только хронике.

## 6. Ecosystem

`Herd` (SoA-массивы + таблица «слот → строка») и пул слотов с поколениями в Life — ровно то,
что делает ECS. Их заменил `ECS::World`:

| Самодельное | ECS |
|---|---|
| `Handle {index, generation}` | `ECS::Entity` |
| `Life::valid(handle)` | `world.valid(entity)` |
| `Life::allocate / release` | `world.create / destroy` |
| `Herd::add / remove / find` + обработка born/died в каждом виде | не нужно: компоненты живут в пулах мира |
| кормёжка: поиск строки охотника в `Herd` | `world.get<Energy>(killer)` — для погибшего охотника `nullptr` |

Rabbits и Foxes больше не читают `eco.born`/`eco.died` ради своих массивов — граф событий стал проще.
Исправлена старая мелочь: Migration срабатывала на тике 0, пока стартовая популяция ещё не родилась.

**3000 тиков:** зайцы 11…347, лисы 10…85, колебания Лотки–Вольтерры сохранились, вымирания нет,
мигрантов 0, ~2000 рождений уложились в 387 слотов. Прогон детерминирован.

## 7. Swarm — стенд производительности

### 7.1. Что делает каждый тик

```
0. Population  — уничтожает сбитых в прошлом тике, рождает новых         (владелец структуры)
1. Grid        — сетка 80×45 клеток сортировкой подсчётом в памяти тика  (MemorySystem)
2. Steering    — стая: разлёт, выравнивание, сплочённость, аттракторы    (соседи только в 3×3)
3. Movement    — интегрирование по плотному массиву пула Body            (ECS)
4. Hazards     — 6 лезвий, кандидаты из сетки → swarm.hit (SoA)           (EventSystem)
render         — 50 000 квадов одним батчем                              (RendererSystem)
```

Компонент агента `Body {position, velocity}` — 16 байт. Горячие системы идут прямо по
`pool.components()`: это самый быстрый путь ECS, без поиска в других пулах.

### 7.2. Сетка в памяти тика

Сетка строится заново каждый тик: счётчики по клеткам, префиксные суммы, раскладка.
Все массивы (≈1.2 МиБ на 50 000 агентов) берутся из `app.tick_arena()`:
- выделение — сдвиг указателя;
- счётчики клеток уже нулевые (ZII), обнулять их не надо;
- освобождение — один `reset()` после тика; **ни одного malloc за всё время работы**.

Сетка хранит копию позиций и скоростей, отсортированную по клеткам. Steering читает снимок
и пишет скорость **только своего** агента — результат не зависит от порядка обхода.

### 7.3. Замеры

GCC 14, RelWithDebInfo, **один поток**, `--no-draw` (без отрисовки агентов):

| Система | 50 000 агентов, мс/тик | нс на агента | 200 000 агентов, мс/тик |
|---|---|---|---|
| grid | 1.16 | 23 | 5.0 |
| steering | 16.8 | 336 | 68.9 |
| movement | 0.16 | 3.2 | 0.65 |
| hazards | 0.02 | 0.3 | 0.06 |
| population | 0.03 | 0.5 | 0.12 |
| **тик целиком** | **18.2** | **364** | **74.7** |
| доля бюджета 30 Гц (33.3 мс) | **55%** | | 224% |

Рост линейный: цена агента не зависит от плотности толпы, потому что просмотр соседей ограничен
48 кандидатами. Отрисовка 50 000 квадов — ~1.5 мс CPU на кадр (подготовка батча; время GPU не входит).

**Почему `--no-draw`.** В контейнере нет видеокарты, и программный OpenGL (Mesa llvmpipe) растеризует
кадр в нескольких потоках — они отнимают ядра у тика и завышают замеры. На настоящей видеокарте
отрисовка асинхронна, и флаг не нужен.

**Устаревшие ссылки.** Первая версия считала попадания по уже уничтоженным агентам почти в каждом
тике (53 842 «устаревших» из ~109 000). Причина — порядок систем: сбитый агент ещё жил, когда лезвия
проверяли следующий тик. Population перенесена в начало тика: теперь устаревшие попадания — только
когда агента задело два лезвия сразу (единицы за прогон). Это наглядный пример того, что поколение
делает ошибку безопасной, но не отменяет необходимости думать о порядке.

### 7.4. Что показывает стенд

- **ECS:** 90% тика — Steering, а не «накладные расходы ECS»: movement по пулу стоит 3 нс на агента.
- **MemorySystem:** временная память тика не видна в замерах вообще — это и есть результат.
- **EventSystem:** сотни попаданий за тик в SoA-канале — сотые доли миллисекунды.
- **Узкое место — один поток.** Steering читает общий снимок и пишет только свою строку:
  его можно разбить на куски по ядрам без блокировок. По оценке, на 8 ядрах 200 000 агентов
  уложились бы в бюджет тика (~69 / 8 ≈ 9 мс на Steering + ~6 мс остального). Это прямой следующий
  шаг — job system.
