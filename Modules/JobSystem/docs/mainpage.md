# JobSystem — задачи и параллельные циклы FluxEng {#mainpage}

JobSystem раздаёт работу по ядрам процессора и при этом **не ломает детерминизм** игры:
результат параллельного цикла одинаков при 0, 1 и 16 потоках.
Подключение: `#include <JobSystem/JobSystem.hpp>`, CMake-цель `engine::JobSystem`.
Зависимости: MemorySystem (временные арены потоков) и `Threads::Threads`.

## Три уровня API

| Уровень | Что это | Когда |
|---|---|---|
| JobSystem::Scheduler + JobSystem::JobCounter | пул потоков, `run(counter, job)` / `wait(counter)` | разнородные задачи: загрузка, генерация, ИИ |
| JobSystem::TaskGroup | счётчик + RAII-ожидание | «запусти эти три вещи и дождись» |
| JobSystem::parallel_for / JobSystem::parallel_reduce / JobSystem::ChunkBuffers | цикл по диапазону, нарезанный на куски | системы ECS: движение, физика, поиск целей |

## Как это устроено

- **Фоновые потоки** (по умолчанию ядра − 1) берут задачи из общей очереди.
- **wait() не спит, а помогает**: пока счётчик не обнулился, ждущий поток сам выполняет задачи из очереди.
  Поэтому задача может запустить подзадачи и дождаться их — вложенный `parallel_for` не блокируется.
- **parallel_for** не кладёт в очередь задачу на каждый кусок: запускается не больше `threads()` помощников,
  каждый забирает номера кусков одним `fetch_add`. Вызывающий поток работает наравне с ними.
- **`threads = 0`** — всё выполняется в вызывающем потоке, по порядку. Это режим отладки и эталон
  для сравнения «1 поток против N».
- **Исключения** из задач не теряются: первое сохраняется в счётчике и перебрасывается из `wait()`.
- **Временная память**: у каждого потока своя MemorySystem::Arena (`scheduler.scratch()`), выделение без блокировок.

## Детерминизм

Диапазон `[0, count)` режется на куски по `grain`: кусок `i` — это `[i·grain, min((i+1)·grain, count))`.
Границы зависят только от `count` и `grain`. Правила, при которых результат не зависит от числа потоков:

1. Кусок **читает** общие данные и **пишет только свои** элементы (строку `i` массива, свой буфер).
2. То, что надо собрать (события, суммы), кусок пишет в **свой** буфер — JobSystem::ChunkBuffers,
   частичный результат JobSystem::parallel_reduce.
3. Сливает буферы **один поток в порядке номеров кусков** — `ChunkBuffers::for_each`.

Даже сумма `float` (неассоциативная!) получается побитово одинаковой: порядок сложения фиксирован.

```cpp
JobSystem::ChunkBuffers<Hit> hits;
hits.reset(JobSystem::chunk_count(bullets.size(), 512));
JobSystem::parallel_for(jobs, bullets.size(), 512, [&](std::size_t begin, std::size_t end, std::size_t chunk) {
    for (std::size_t i = begin; i < end; ++i)
        if (auto hit = trace(bullets[i])) hits[chunk].push_back(*hit);
});
hits.for_each([&](const Hit& h) { bus.write(h); });   // один поток, порядок кусков
```

## Как выбрать grain

Кусок должен занимать **десятки микросекунд**: тогда накладные расходы (fetch_add, пробуждение потока)
— доли процента. Для простых циклов (сложение векторов) это тысячи элементов, для тяжёлых (поиск
соседей) — сотни. Бенчмарк `JobSystemBenchmarks` показывает обе крайности.

## Чего модуль не делает (сознательно)

- Нет приоритетов, зависимостей-графов и work-stealing деков: общая очередь под мьютексом проще
  и при «весомых» кусках не является узким местом — куски раздаются атомарным счётчиком, а не очередью.
- Нет файберов: `wait()` помогает выполнять задачи вместо переключения стека.
