# JobSystem — конспект для изучения и переписывания

Читается вместе с кодом: `src/include/JobSystem/{Scheduler,Parallel,JobSystem}.hpp` и `src/code/Scheduler.cpp` (~550 строк). Зависит от `MemorySystem` (арена на поток).

## 1. Зачем модуль и главная идея

Нужно распараллелить тяжёлые циклы (движение роя, обход чанков), **не потеряв детерминизм**: результат при 0, 1 и 16 потоках обязан быть побитово одинаковым — иначе ломаются записи и сеть.
Идея в двух правилах:

1. **Нарезка зависит только от `count` и `grain`**, а не от числа потоков и не от того, кто какой кусок взял.
2. **Слияние результатов идёт по номеру куска**, а не по времени завершения.

Если каждый кусок пишет только свои данные, итог не зависит от планирования. Второй принцип планировщика: **ждущий поток не спит, а помогает** выполнять задачи — поэтому вложенные `parallel_for` не блокируют друг друга.

## 3. Как устроено

### 3.1 `Scheduler`
- `SchedulerConfig{threads, scratch_bytes}`: `threads` — **фоновые** потоки (по умолчанию ядра − 1), `0` — всё в вызывающем потоке (отладка и сравнение «1 против N»). `concurrency() = threads() + 1`, потому что ждущий поток тоже работает.
- Одна общая очередь `std::deque<Task>` под мьютексом. Задача = `std::function<void()>` + указатель на `JobCounter`.
- `run(counter, job)`: `counter.pending++`; без фоновых потоков — выполнить сразу; иначе положить в очередь и разбудить спящего, **только если** `m_sleeping > 0` (чтобы не платить системным вызовом на каждой задаче).
- `wait(counter)`: пока счётчик не ноль — берёт задачи из очереди и выполняет (`helped_while_waiting`); если очередь пуста, 64 раза `cpu_relax`, потом `yield`. В конце перебрасывает **первое** исключение, сохранённое счётчиком.
- Рабочий поток: берёт задачу; если нет — до 4096 раз крутится `pause` (задачи следующей системы того же тика подхватываются без пробуждения), затем засыпает на `condition_variable`.
- Защита от «потерянного пробуждения»: поток, собравшийся спать, увеличивает `m_sleeping` **под мьютексом** и перепроверяет очередь; `run` кладёт задачу под тем же мьютексом, а потом читает `m_sleeping` (seq_cst). Либо спящий увидит задачу, либо `run` увидит спящего.
- `execute`: исключение ловится и кладётся в счётчик (`capture` — первое выигрывает); **задача уничтожается (`job = nullptr`) до уменьшения счётчика**, потому что после обнуления ждущий поток может выйти из `wait` и снять со стека то, на что ссылаются захваты. Уменьшение с `memory_order_release`, чтение в `done()` — `acquire`: всё записанное задачей видно ждущему.
- `scratch()`: у каждого потока своя `Arena` (тег `Jobs`); `this_thread_index()` — 0 для «вызывающего» (не рабочего) потока, 1…N для рабочих (через `thread_local`). Нерабочие потоки делят арену 0 → пользоваться ею можно только из одного такого потока.

### 3.2 `JobCounter`, `TaskGroup`
`JobCounter{}` — «ничего не запущено» (ZII): `wait` возвращается сразу. Хранит первое исключение. `TaskGroup` — счётчик + планировщик; **деструктор ждёт и проглатывает исключения** — вызывай `wait()` явно, если они важны.

### 3.3 `parallel_for`
- Куски: `[c·grain, min((c+1)·grain, count))`; `grain=0` считается за 1.
- Один кусок или нет потоков → последовательный цикл в вызывающем потоке (исключение летит напрямую).
- Иначе: атомарный счётчик `next`; каждый исполнитель крутит `drain` (`fetch_add` → кусок). Запускается `min(threads, chunks−1)` помощников, вызывающий поток тоже делает `drain`, потом `wait(helpers)`. Очереди на кусок нет — один `fetch_add`.
- Тело может иметь сигнатуру `(begin, end)` или `(begin, end, chunk)` — выбирается `if constexpr` через `is_invocable`.
- **Исключения.** Если бросает вызывающий поток, `next` ставится в конец (необработанные куски не берутся), помощники дорабатывают начатое, после `wait` исключение перебрасывается. Если бросает помощник — он прекращает `drain`, остальные продолжают, а `wait(helpers)` перебросит его ошибку. Комментарий в заголовке («остальные куски всё равно выполняются») описывает это неточно: после ошибки часть кусков может остаться невыполненной. Не рассчитывай на частичный результат после исключения.

### 3.4 `parallel_reduce`
`partial[chunk] = map(begin, end)` параллельно, затем **последовательное** слияние `combine` по возрастанию номера куска. Из-за фиксированного порядка результат одинаков даже для `float` (в проекте float внутри симуляции не используется, но свойство полезно для рендера и статистики).

### 3.5 `ChunkBuffers<T>`
Выходные буферы по одному на кусок: кусок пишет только в `buffers[chunk]` (без замков), затем один поток обходит `for_each` в порядке кусков. Каждый слот выровнен на 64 байта (`alignas(64)`), чтобы заголовки соседних `std::vector` не делили кэш-линию (false sharing). `reset(chunks)` сохраняет ёмкость между тиками — в устойчивом режиме аллокаций нет.

## 4. Как использовать

```cpp
JobSystem::Scheduler jobs({.threads = 4});

// 1. Параллельный цикл: каждый кусок пишет только свои элементы
JobSystem::parallel_for(jobs, bodies.size(), 1024, [&](std::size_t b, std::size_t e) {
    for (std::size_t i = b; i < e; ++i) bodies[i].pos += bodies[i].vel * dt;
});

// 2. Свёртка с детерминированным порядком
auto sum = JobSystem::parallel_reduce(jobs, n, 4096, std::uint64_t{0},
    [&](std::size_t b, std::size_t e) { std::uint64_t s = 0; for (auto i = b; i < e; ++i) s += v[i]; return s; },
    [](std::uint64_t a, std::uint64_t b) { return a + b; });

// 3. Порождение событий без блокировок
JobSystem::ChunkBuffers<Hit> hits;
hits.reset(JobSystem::chunk_count(n, 1024));
JobSystem::parallel_for(jobs, n, 1024, [&](std::size_t b, std::size_t e, std::size_t chunk) { /* hits[chunk].push_back(...) */ });
hits.for_each([&](const Hit& h) { bus.emit(h); });   // один поток, порядок кусков

// 4. Свои задачи
JobSystem::TaskGroup g(jobs);  g.run([&]{ physics.step(); });  g.run([&]{ audio.mix(); });  g.wait();
```

Где это в проекте: `Runtime::jobs()` (`RuntimeSystem`), `Core::App::jobs()`; `WorldRender` строит меши чанков параллельно; игры Swarm/Siege используют `parallel_for` для Steering/Movement.

## 5. Что менять осторожно

- **Детерминизм держится на двух инвариантах** (§1). Если «оптимизируешь» раздачу кусков по числу потоков или сливаешь по готовности — тесты `1 против N потоков` покажут расхождение, но только если данные чувствительны к порядку.
- Грануляция: слишком мелкий `grain` съедает выигрыш. Рабочая прикидка — десятки микросекунд на кусок.
- Не вызывай `wait` из задачи на счётчик, который она сама пополняет, не понимая последствий: ждущий помогает, но цикл ожидания всё равно обязан завершиться.
- Порядок «уничтожить задачу → уменьшить счётчик» в `execute` и память `release/acquire` — не косметика; это защита от use-after-scope на стеке ждущего.
- Очередь одна и общая: при очень большом числе мелких задач мьютекс станет узким местом. Если понадобится work stealing — это отдельная архитектура (очередь на поток, кража).

## 6. Упражнения для переписывания

1. Убери «помощь при ожидании» (`wait` просто спит) и запусти вложенный `parallel_for` — получишь взаимную блокировку. Проверь на тесте.
2. Замени spin-then-sleep на «сразу спать» и измерь бенчмарк `JobSystem` — на какой нагрузке разница заметна?
3. Исправь расхождение в документации/поведении исключений: сделай так, чтобы после ошибки гарантированно выполнялись **все** куски (или, наоборот, документируй остановку).
4. Реализуй `parallel_scan` (префиксные суммы) с тем же правилом «границы зависят только от count и grain».
5. Добавь очередь на поток с кражей и сравни с одной общей очередью на `Swarm`.
