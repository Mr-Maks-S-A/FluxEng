# Replay — конспект для изучения и переписывания

`src/include/Replay/Replay.hpp` (354 строки, почти всё API в одном заголовке) и `src/code/Replay.cpp` (~640 строк). Зависит от `Math` (`content_hash`, `FLUX_ASSERT`) и `EventLog` (формат файла).

## 1. Зачем и главная идея

Мир меняется **только командами внутри тика**, а симуляция детерминирована → **сид + команды каждого тика полностью задают прогон**. Отсюда:
- **запись:** сид и команды пишутся в файл по ходу игры;
- **повтор:** команды берутся из файла вместо ввода, и **хеши состояния** на последнем тике должны совпасть с записанными;
- **любой баг** воспроизводится файлом записи; два прогона сравниваются по хешам подсистем и называют, **какая** подсистема разошлась.

Тот же интерфейс «команды на тик» использует сеть (`Net::Lockstep`) — команда, которую можно записать, можно и переслать.

## 2. Основные типы

| Тип | Роль |
|---|---|
| `Command` | **16 байт**: `u16 type`, `i16 arg`, `i32 x, y, z`; смысл полей — в схеме игры (`static_assert(sizeof == 16)`) |
| `StateHashes` / `NamedHash` | до 8 пар «имя (до 16 байт) → хеш»: `terrain`, `mana`, `characters`, `spells`, `rng`, `tick`; `differing(other)` — какие разошлись; `describe` |
| `CommandRegistry` / `CommandSchema` / `CommandField` | имена команд и полей (`Int` или `Fixed`) — попадают **в файл** (самоописываемость: инструменты читают запись без знания игры); `format(command)` → «move dx=1 dz=0» |
| `Blob` | `{hash, bytes}` — большие данные, на которые команда ссылается по хешу (программа заклинания) |
| `Recording` | сид, число тиков, трейлер-хеши, схемы, блобы, команды (параллельные `m_ticks`/`m_commands`); `add`, `at(tick)`, `save`, `load`, `load_with_info`, `repair_file` |
| `Session` | режим `Off`/`Record`/`Replay`; `begin_tick`, `finish`, `add_blob`, `from_args`, `record`, `replay` |
| `Driver<Sim>` | один вызов на тик вместо ручной склейки сессии, журнала и симуляции |
| `FlightRecorder` | кольцо последних тиков (команды + хеши); дамп в файл при `FLUX_ASSERT` |
| `inspect`, `describe`, `diff` | просмотр записи, отчёт о чтении, первое расхождение двух записей |

Концепты: `Simulatable` (`tick(span<Command>)`, `tick_number()`, `hashes()`), `BlobSink` (`provide_blob(bytes)` — необязательно).

## 3. Как устроено

### 3.1 Файл записи — журнал EventLog
Типы записей журнала: `meta` (1: версия + сид), `schema` (2), `command` (3: тик лежит в записи журнала, в payload — 16 байт), `trailer` (4: число тиков + хеши подсистем — **запись закончена штатно**), `blob` (5: хеш + байты). Блоб пишется **раньше** команды, которая на него ссылается — порядок журнала это гарантирует.
- Команды пишутся **по ходу игры**, раз в 60 тиков (`flush_interval_ticks`) делается `flush` → при падении теряется не больше секунды.
- Оборванная запись читается: `complete = false`, финальных хешей нет, повтор идёт до последней команды, сверять нечего.
- Повреждённые блоки восстанавливаются по чётности; `Recording::repair_file` / `ReplayTool repair` переписывают их на месте.
- Если команды потеряны **сверх избыточности**, `Recording::load` отказывает («повтор невозможен» — молча разошедшийся повтор хуже ошибки); `load_with_info` отдаёт остаток и отчёт `LoadInfo::recovery`.
- Блоб с несовпавшим хешем при чтении **отбрасывается** (подмена не пройдёт тихо). Старые плоские файлы (версии 1–2) читаются (`Format::Legacy`), их хеши получают имена `h0…h2`.

### 3.2 `Session`
- `from_args(args, default_seed, registry)` разбирает `--record f`, `--replay f`, `--seed N`.
- `begin_tick(tick, live)`: **Replay** → команды записи (`at(tick)`), `live` игнорируется; **Record** → `live` добавляется в `m_recording` и в журнал, возвращается `live`; **Off** → `live`.
- `finish(ticks_run, hashes)`: запись → `tick_count`, трейлер с хешами, flush, файл закрывается; повтор → сверка с записанными **по подсистемам** → `Verdict{checked, match, complete, expected, actual, differing[]}`.
- `finished(tick)` — повтор дошёл до конца записи.

### 3.3 `Driver`
`step(live)`: если повтор закончился — `false`, тик не выполняется; иначе `commands = session.begin_tick(tick, live)`, `sim.tick(commands)`, затем `FlightRecorder::push`. При создании в режиме Replay отдаёт симуляции **все блобы записи** (`provide_blob`) — ссылки команд к первому тику уже разрешимы. `submit_blob(bytes)` — в запись и в симуляцию, возвращает хеш для команды; вызывать **до** `step`, в котором уйдёт команда.

### 3.4 `FlightRecorder`
Кольцо (по умолчанию 256 тиков): номер, `command_count`, до 8 команд (остальные отбрасываются), хеши. `install_assert_dump(path)` подключает дамп к `Math::set_assert_handler` — при сбое `FLUX_ASSERT` последние тики сбрасываются в файл. Один на процесс.

### 3.5 Хеши названы
Симуляция сама решает, какие подсистемы различать: `h.add("terrain", ...).add("mana", ...)`. При расхождении повтора отчёт называет подсистему («разошлись подсистемы: mana»); `diff(a, b)` выдаёт первое расхождение (сид, команда, число тиков, хеши).

### 3.6 Блобы
Команда 16 байт и не вмещает граф/программу. Блоб по **хешу содержимого** (`Math::content_hash`) даёт: одну копию на запись, дедупликацию (повтор правки = тот же хеш), проверку целостности и доставку независимо от команд. Цена — порядок: блоб обязан прийти раньше команды (в записи это порядок журнала, в сети — «ворота» `ready()`).

## 4. Как использовать

```cpp
Replay::CommandRegistry registry;
SpellSim::register_commands(registry);
auto session = Replay::Session::from_args(args, /*seed*/ 1, &registry).value();   // --record f | --replay f | --seed N
Replay::FlightRecorder flight(256);
Replay::Driver driver(sim, session, &flight);

// каждый тик:
if (!driver.step(live_commands)) quit();                // при повторе live игнорируется
// в конце:
auto verdict = driver.finish().value();
std::puts(Replay::describe(verdict, session.mode(), ticks, commands).c_str());

const std::uint64_t hash = driver.submit_blob(program_bytes);               // до тика
live.push_back(SpellSim::set_program_command(slot, hash));                  // в команде только хеш
```
Где это в проекте: `FirstSpell`, `RuneCell2`, `SpellSim`-golden (`SpellSim/tests/golden`), `Challenge::play(level, solution, Session*)`, `Net::Lockstep` (команды и блобы по сети), `ReplayTool inspect | diff | repair`.

## 5. Что менять осторожно

- **`Command` ровно 16 байт** — формат файла и сети; расширение (например, `player_id`) = новая версия формата и всех мест, где эта структура сериализуется.
- **Порядок «блоб до команды»** — инвариант; нарушишь — повтор падает на команде с неизвестным хешем.
- `Verdict.differing` строится по **именам** хешей: переименование подсистемы в симуляции ломает сверку со старыми записями (они сравнятся «не найдено»).
- `StateHashes::capacity = 8` и имена до 16 байт — потолок; новая подсистема сверх 8 требует расширения формата трейлера.
- Повтор **обязан** исполнять тот же код тик в тик: любая недетерминированность симуляции (float, порядок хеш-таблиц, потоки) проявится как расхождение хеша. Эталоны: `tools/update_golden.sh`.
- `Session::finish` в режиме Record закрывает файл — после него записывать нельзя.
- `FlightRecorder::install_assert_dump` глобален — не более одного на процесс.

## 6. Упражнения для переписывания

1. Напиши `ReplayTool diff` с нуля через `Recording::load` и `diff`, и найди расхождение двух прогонов с разным числом потоков (должно быть пусто).
2. Добавь `player_id` в `Command` (версия формата 2) и сохрани чтение старых файлов: как отличить версию?
3. Реализуй «перемотку»: снимок состояния каждые N тиков + повтор с ближайшего снимка (что нужно от `Simulation`?).
4. Замени `Driver` обобщённым `Stepper<Sim, Source>` (конспект 16, п. 3.1) и убедись, что golden не меняются.
5. Сделай сжатие блобов (одинаковые программы в разных слотах уже дедуплицируются — измерь выигрыш на записи `RuneCell2`).
